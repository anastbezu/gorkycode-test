# Правила работы в репозитории

Короткий свод правил для всей команды и для ваших AI-агентов. Если правило мешает — пишите техлиду (Родион), а не обходите его.

---

## 1. Ветки

```
main        ← рабочая версия для демо и деплоя. Только через PR из develop, на контрольных точках.
  └─ develop   ← интеграция. Сюда вливаются все задачи. Должна запускаться.
       ├─ feature/agent-01-razbor-dat
       ├─ feature/backend-02-spisok-za-period
       ├─ fix/backend-03-chasovoy-poyas
       └─ docs/contracts-api
```

| Ветка | Кто пишет | Как попадает код |
|---|---|---|
| `main` | никто напрямую | PR `develop → main`, мержит техлид |
| `develop` | никто напрямую | PR из рабочих веток, ревью техлида |
| `<тип>/<задача>` | исполнитель задачи | обычные коммиты |

**Имя рабочей ветки:** `<тип>/<имя файла задачи без .md>`, например `feature/agent-01-razbor-dat`.
Типы: `feature/` — новая функциональность, `fix/` — исправление, `docs/` — документация, `chore/` — настройка, зависимости, CI.

**Одна задача (`docs/tasks/…`) = одна ветка = один PR.** Не копите в одной ветке несколько задач.

---

## 2. Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<модуль>): <что сделано>

feat(agent): разбор относительных дат «завтра», «в пятницу»
fix(backend): время встречи сохранялось без часового пояса
docs(contracts): добавлен формат ChatResponse
test(search): проверочные запросы для гибридного поиска
```

- **Типы:** `feat`, `fix`, `docs`, `test`, `refactor`, `chore`.
- **Модули:** `agent`, `search`, `backend`, `db`, `api`, `voice`, `frontend`, `devops`, `contracts`, `docs`.
- Описание — по-русски или по-английски, в повелительном/прошедшем времени, до ~70 символов.
- Коммитьте маленькими логичными шагами. «fix», «правки», «wip» — плохие сообщения.

---

## 3. Pull Request

1. Перед PR подтяните свежий `develop` в свою ветку (см. §6) и убедитесь, что всё запускается.
2. PR открывается **в `develop`**. Заголовок — в формате коммита.
3. Заполните шаблон PR: что сделано, ссылка на файл задачи, как проверить.
4. **Ревью техлида обязательно.** Замечания исправляете новыми коммитами в ту же ветку.
5. Мерж — **Squash and merge**, ветку после мержа удаляем.
6. PR поменьше: ориентир до ~400 строк изменений. Больше — разбейте задачу.
7. Конфликты при мерже решает автор PR.

---

## 4. Нельзя

- Пушить напрямую в `main` и `develop`.
- `git push --force` в чужие и общие ветки.
- Коммитить секреты: `.env`, API-ключи, токены. **Репозиторий публичный** — утёкший ключ считается скомпрометированным сразу.
- Менять файлы в `docs/contracts/` без согласования с техлидом — от них зависят чужие модули.
- Коммитить большие файлы: модели, дампы БД, аудио, виртуальные окружения.
- Добавлять зависимости молча — новая библиотека упоминается в описании PR.

---

## 5. Работа с AI-агентами

- Дайте агенту: **файл своей задачи** (`docs/tasks/…`), **описание своего модуля** (`docs/modules/…`), **контракты** (`docs/contracts/`) и **этот файл**.
- Вы отвечаете за код, который пушите, а не агент. Прочитайте дифф перед коммитом.
- Не коммитьте служебные файлы агентов (заметки, логи, временные скрипты), если они не нужны проекту.
- Агент не должен трогать чужие модули и контракты — если ему «надо», это вопрос к техлиду.

---

## 6. Ежедневный цикл

```bash
# начать задачу
git checkout develop
git pull
git checkout -b feature/<задача>

# установка зависимостей бэкенда (один раз или при обновлении)
cd backend && uv sync

# запуск проверок и локального сервера
uv run ruff check
uv run pytest
uv run uvicorn main:app --reload

# в процессе
git add <файлы>
git commit -m "feat(<модуль>): <что сделано>"
git push -u origin feature/<задача>

# подтянуть свежий develop в свою ветку (каждый день и перед PR)
git fetch origin
git merge origin/develop
```

Дальше — PR на GitHub в `develop`.

---

## 7. Секреты и окружение

- Все переменные окружения перечислены в `.env.example` (без значений).
- Свои значения — в локальном `.env` (он в `.gitignore`).
- Добавили новую переменную — добавьте её имя в `.env.example` в том же PR.

---

## 8. Задача готова, когда

- код в `develop` через одобренный PR;
- выполнены критерии готовности из файла задачи;
- запускается локально по инструкции из README;
- если изменилось устройство модуля — обновлён `docs/modules/<модуль>.md`.

## Где что

| Что | Где |
|---|---|
| Что нужно сделать (задачи) | `docs/tasks/` |
| Как устроены модули | `docs/modules/` |
| Границы модулей (контракты) | `docs/contracts/` |
| Архитектура | `docs/architecture.md` |
| Учёт задач, сроки, статусы | доска YouGile |
| Вопросы и уведомления | чат команды в Telegram |
