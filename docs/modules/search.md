# Модуль search: поиск записей

Владелец: Родион. Контракт — [`docs/contracts/search.md`](../contracts/search.md). Решения — строки «Поиск по старым записям» и «Цель изменения» в [`docs/decisions.md`](../decisions.md).

## Устройство

```
backend/search/
├── __init__.py     search(), find_target() — всё, что видит агент
├── core.py         отбор по фильтрам, уровни «точно» и «похожие», сужение по времени, порядок
├── text.py         уровень «точно»: значимые слова запроса и сравнение со словами названия
├── vectors.py      таблица text_embeddings: досчитать векторы, сходство с запросом (pgvector)
├── embeddings.py   модель эмбеддингов: текст → 312 чисел
└── warmup.py       прогрев при старте сервера: модель и векторы стартового набора
backend/eval/search_eval.py       проверочные наборы и отчёт
backend/eval/search_cases.py      расширенный набор: случаи по группам и эталон
```

Обе функции работают одинаково:

1. **SQL отбирает записи пользователя по фильтрам** — тип, период, статус. Текст сравнивается только с ними.
2. **Уровень «точно»** — в названии есть каждое значимое слово запроса. Нашлось — ответ из точных.
3. **Уровень «похожие»** — точных нет: сходство векторов названий с вектором запроса не ниже порога.

Пример на стартовом наборе (там искажённые падежи: «Позвонить Дмитрием»):
- «Дмитрий бюджет» → «точно»: «Напомнить Дмитрию про бюджет» — «Дмитрий» и «Дмитрию» одной основы;
- «звонок Дмитрию» → «звонок» не совпадает с «позвонить» ни по основе, ни по буквам, точных нет; по смыслу «Позвонить Дмитрием» близко — «похожие», агент отвечает «точно не нашёл, похожие: …»;
- «встреча с дизайнером» → дизайнеров в данных нет: точных нет, похожие — «Встреча с …» других людей или пусто.

## Уровень «точно» — `text.py`

Слово запроса совпадает со словом названия, если:
- у них **одна основа** по Snowball russian — правила отрезают окончания: «юристами» ↔ «юристом»;
- у них **одна словарная форма** по pymorphy3 — словарь русских слов со всеми формами: «Сергею» ↔ «Сергеем», «Иван» ↔ «Иваном» (основы Snowball у них разные: `серг` / `серге`, `ива` / `иван`);
- это **опечатка** — буквы почти те же (`rapidfuzz.fuzz.ratio ≥ 85`) и хотя бы одно из слов не словарное: «Дмтрий» ↔ «Дмитрий». Два словарных слова с разными формами — разные слова, даже если отличаются одной буквой: «Виктором» ↔ «Вектором» не совпадают.

Перед сравнением — нижний регистр и «ё» → «е». Служебные слова («с», «по», «про») — список стоп-слов Postgres `russian` — не значимы. Запрос без значимых слов не совпадает ни с чем.

**Слова типа записи** («встречу», «задачу», «напоминание», «дело») совпадают, если слово есть в названии **или запись этого типа**: «встречу с Севером» находит «Созвон с Севером» (тип — встреча), «задачу про смету» — «Согласовать смету с Максимом». А «отмени встречу с Алексеем по CRM» не находит задачу «Обсудить CRM с Алексеем»: без этого правила она нашлась бы как единственная точная и была бы отменена. «Задачу» — задачи и напоминания, как у агента.

**Почему не полнотекст Postgres.** Он сравнивает только основы Snowball, а они не сводят падежи имён. «Каждое слово по основе, словарной форме или как опечатка» в SQL не выразить. Записей у пользователя около тысячи — сравнение в Python занимает миллисекунды.

**Почему сравнение по словам, а не нечёткое по фразе.** Нечёткое сравнение целой фразы (как в голосовом ассистенте OVOS: максимум из `ratio`, `partial_ratio`, `token_sort_ratio`) в замере дважды выбрало чужую запись: «созвон с Севером по CRM» → «Созвон с Севером по новому продукту». Сравнение по словам требует каждое слово — «CRM» в названии нет, значит, не та запись.

## Уровень «похожие» — `embeddings.py`, `vectors.py`

- **Модель** — [`sergeyzh/rubert-mini-frida`](https://huggingface.co/sergeyzh/rubert-mini-frida) (MIT), ревизия закреплена. 312 чисел на текст, ~10 мс на запрос, без сети. Запускается через sentence-transformers на **PyTorch CPU**: torch ставится с индекса PyTorch без CUDA (`[tool.uv.sources]` в `pyproject.toml`) — torch с PyPI под Linux тянет пакеты CUDA на гигабайты.
- **Префиксы задач** — запрос кодируется с `search_query: `, название — с `search_document: `. Их подставляет sentence-transformers по имени (`prompt_name="query"` / `"passage"`). Дописывать префикс к тексту руками нельзя: у модели префикс по умолчанию `categorize: `, и текст ушёл бы с двумя префиксами.
- **Эмбеддится только название.** Тип и даты — фильтры, в векторе они ничего не дают.
- **Вектор — на текст, а не на запись.** Таблица `text_embeddings`: ключ — модель и md5 текста. 376 разных названий стартового набора считаются один раз на всех пользователей; переименование даёт новый текст и новый вектор.
- **Векторы досчитывает поиск сам**, перед уровнем «похожие», только для текстов без вектора. Сервисы записей поиск не вызывают. Запись — в транзакции вызывающего: векторы сохраняются вместе с репликой, один коммит на реплику (`decisions.md`, «Доступ к БД»). Два запроса на один текст одновременно — второй `INSERT` ничего не делает (`ON CONFLICT DO NOTHING`).
- **Сходство считает pgvector** — косинус (`<=>`). Индекса по вектору нет: у пользователя ~1000 записей, полный перебор быстрее индекса.
- **Прогрев при старте** (`search/warmup.py`, включает `SEARCH_WARMUP=1` — так в образе): в фоне загружается модель и считаются векторы 376 названий стартового набора, запросы его не ждут. Без прогрева первый поиск «похожих» после деплоя ждал бы загрузку модели, а первый в жизни базы — и векторы: в контейнере на 1 ядре импорт PyTorch и sentence-transformers 9,5 с, загрузка модели 1,1 с, 376 векторов 6,3 с. Без `SEARCH_WARMUP` (тесты, локальный запуск) модель грузится при первом поиске «похожих». Файлы модели скачиваются при сборке образа (`Dockerfile`), в работе сервер в сеть не ходит (`HF_HUB_OFFLINE=1`).
- **Порог «похожих» — 0,45** (`core.SIMILAR_MIN_SCORE`), снят на проверочном наборе: у запросов, которые не нашлись точно, но ответ в данных есть, лучший результат — от 0,485 до 0,82; у запросов без ответа — до 0,464. Порог ниже обоих: пропустить настоящую похожую запись хуже, чем честно ответить «точно не нашёл, похожие: …» там, где ответа нет.

## `search()` — порядок и лимит

- Без фильтра статуса — без отменённых, как список за период.
- Период — по дате записи: начало, а у задачи без начала — срок; `[date_from, date_to)`.
- Порядок (`core._nearest_first`) — от `now`: будущие от ближних к дальним, затем прошедшие от новых к старым, без даты — в конце. «Сейчас» и позже — будущие.
- Точные — все; `limit` задан (так меряет `eval/search_eval.py`, hit@5) — остаются первые по порядку. Раньше точных было не больше 10 и ответ говорил «Нашёл 10 записей», когда их было 43.
- Похожие — не больше `core.SIMILAR_LIMIT` = 10: остаются самые близкие, на экране они идут в том же порядке по дате.

## `find_target()` — цель изменения

- `exact` — только по словам. Похожие по смыслу в `exact` не попадают никогда.
- `when` сужает точные по ступеням: тот же день и время → тот же день → то же время в другой день. День и время — в поясе `when` (пояс пользователя). Записи «на весь день» по времени не совпадают ни с чем.
- `when` ровно в 00:00 — назван только день («в пятницу»): так агент передаёт день без времени, и сравнивается только день. Иначе «в пятницу» нашло бы записи в 00:00 других дней.
- Слова совпали, а под `when` не подошла ни одна — `exact` пуст, в `similar` — до 3 ближайших ко времени `when`.
- Точных по словам нет — в `similar` до 3 ближайших по смыслу.
- `text = None` («отмени всё на завтра») — все записи по фильтрам и `when`.
- Порядок — по дате записи от ранних к поздним, без даты — в конце.

**Известный риск.** Встреча, назначенная ровно на 00:00, при команде «…в пятницу» сравнивается только по дню — как и любая другая запись этого дня.

## Проверочные наборы — `eval/search_eval.py`, `eval/search_cases.py`

```bash
cd backend
uv run python -m eval.search_eval                  # базовый набор: каждый запрос и каждая цель
uv run python -m eval.search_eval --extended       # и расширенный: метрики по группам, примеры ошибок
uv run pytest tests/test_search_quality.py
```

Данные — стартовый набор (1000 записей), пояс Europe/Moscow, «сейчас» — 21.10.2026 12:00 (`docs/test-cases.md`). Нужны PostgreSQL с pgvector и модель в кэше Hugging Face; без модели тесты качества пропускаются с причиной (в CI модели нет — там они пропускаются, все остальные тесты работают с подменой модели из `tests/conftest.py`).

- **Базовый** — 30 запросов с ответом (примеры задания, `docs/test-cases.md` раздел 5 и свои), 6 без ответа, 24 цели изменения. Эталон — регулярные выражения по названию.
- **Расширенный** — 619 запросов и 587 целей по группам граничных случаев: падежи имён и компаний, темы, документы, все пары «человек + тема» (есть и нет в данных), синонимы и сокращения, опечатки, речь со словами-паразитами, несуществующее, фильтры типа и периода, пустые запросы; для целей — одна и несколько записей, с днём и временем, с днём, на котором записи нет, сочетания, которых нет, «встречу» там, где есть только задача, «верни» среди выполненных, «всё на этот день». Эталон считается независимо от поиска: названия датасета собраны из шаблонов («Встреча с {человек} по {тема}» …), каждое разобрано на понятия (действие, человек, компания, тема, документ), формы слов в запросах выписаны вручную.

Тесты требуют то, что нельзя нарушать: базовый — найдено ≥ 29 из 30, ни одного «точно» без ответа, ни одной чужой цели; расширенный — ни одной чужой цели и ни одного «точно» без ответа. Остальное — метрики отчёта.

### Результаты (2026-10-29)

| Набор | Показатель | Результат |
|---|---|---|
| базовый | найдено (из 5 результатов) | 29 из 30 — не найдено «ТЗ» |
| базовый | «точно» на запросах без ответа | 0 из 6 |
| базовый | цели: верно / чужая | 24 из 24 / 0 |
| расширенный | найдено (из 10 результатов, как зовёт агент) | 439 из 457 — 96% |
| расширенный | «точно» на запросах без ответа | 0 из 162 |
| расширенный | цели: чужая запись | 0 из 587 |
| расширенный | цели: одна запись исполнена сразу | 77 из 77 |

По группам расширенного набора: падежи имён и компаний, темы, документы, «человек + тема», «компания + тема», действие + человек, все фильтры — найдено 100%. Слабые места (чужого не находит, но и нужное тоже):
- **сокращения и жаргон** — «КП», «ТЗ», «презентуха», «летучка», «финансы»: модель их не связывает (группа — 16 из 21);
- **опечатка в слове, сказанном в другом падеже**: «хактаон» против «по хакатону», и опечатки в одиночном имени — «Маряи», «Дмтрий» (группа — 27 из 37);
- **«СРМ» кириллицей** и слово-паразит, которого нет в стоп-словах («типа отчет») — 10 из 12. В жизни запрос для поиска формулирует агент, и слова-паразиты он отбрасывает.

Набор синтетический: формы слов и запросы составлены по датасету, а не записаны с живой речи. Порог «похожих» стоит переснять на живых фразах после распознавания речи.

## Пересчитать векторы

Векторы привязаны к модели и ревизии (`embeddings.MODEL_KEY`). Новая модель или ревизия — новые ключи: старые векторы не используются, новые досчитываются при первых поисках. Удалить старые:

```sql
DELETE FROM text_embeddings WHERE model <> '<новый MODEL_KEY>';
```

Порог «похожих» снят для текущей модели — при смене модели переснять его на проверочном наборе.
