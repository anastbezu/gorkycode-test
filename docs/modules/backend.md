# Модуль backend: хранилище

Владелец: Денис. Контракт данных — [`docs/contracts/data-model.md`](../contracts/data-model.md).

## Устройство

```
backend/
├── schemas/          Pydantic-модели из docs/contracts/ — единственное, что видят агент, API и поиск
├── db/
│   ├── models.py     ORM-модели SQLAlchemy 2 (только для сервисов бэкенда, наружу не отдаются)
│   └── session.py    движок и сессии, адрес из DATABASE_URL
├── services/         бизнес-логика: записи (records.py), состояние разговора (conversation.py),
│                     пользователи и вход (accounts.py), демо-учётки (demo_accounts.py),
│                     срок хранения (retention.py)
├── stt/              распознавание речи для /api/stt: запись, лимит частоты, клиент Gemini
├── alembic/          миграции схемы
├── scripts/          команды: демо-учётки, чистка, ручная загрузка датасета
└── tests/            pytest
```

Граница: сервисы читают строки `db.models.*` и отдают наружу `schemas.Record` /
`schemas.ConversationState` через `Model.model_validate(row)` (`from_attributes=True`).

## Схема базы

### `records` — задачи, встречи, напоминания

| Колонка | Тип | Правила |
|---|---|---|
| `id` | uuid | PK, `uuid4` |
| `user_id` | uuid | NOT NULL, `users.id` — гость или учётка (внешнего ключа нет, см. «Учётки и вход») |
| `type` | varchar(16) | `task` / `meeting` / `reminder` |
| `title` | text | не пустой |
| `start_at` | timestamptz | обязателен у `meeting` |
| `end_at` | timestamptz | позже `start_at` |
| `all_day` | boolean | default `false`; дата без времени — `true`, а не полночь |
| `deadline` | timestamptz | срок задачи, не начало |
| `status` | varchar(16) | `active` / `done` / `cancelled`, default `active` |
| `cancelled_at` | timestamptz | когда отменили; пусто, если не отменена (с `0004`) — для чистки через 30 дней |
| `created_at`, `updated_at` | timestamptz | `now()`; `updated_at` обновляется при изменении |

Индексы: `(user_id, start_at)` — списки за период; `(user_id, status)` — активные / выполненные.

### `conversation_states` — состояние разговора

| Колонка | Тип | Смысл |
|---|---|---|
| `conversation_id` | uuid | PK |
| `user_id` | uuid | индекс |
| `focus_record_id` | uuid | FK → `records.id`, `ON DELETE SET NULL`; «её», «эту встречу» |
| `shown` | uuid[] | записи, показанные пользователю под номерами: номер N — `shown[N - 1]` (с `0003`) |
| `last_action` | jsonb | последнее изменение (`LastAction`): для поправки, «верни» и «не эту, а ту» (с `0003`) |
| `pending` | jsonb | черновик действия агента (`LLMAction`) при уточнении |
| `pending_skipped` | boolean | прошлая реплика была не про черновик; default `false` (с `0003`) |
| `candidates` | uuid[] | записи, из которых пользователь выбирает |
| `missing` | text[] | каких полей не хватает, напр. `{start}` |
| `awaiting` | varchar(16) | `answer` / `choice` / NULL |
| `updated_at` | timestamptz | время последнего изменения |

## Принятые решения

- **`start_at` / `end_at` в БД, `start` / `end` в Python.** `end` — зарезервированное слово SQL:
  в сыром SQL (поиск) его пришлось бы всегда брать в кавычки. Атрибуты ORM и поля Pydantic
  называются как в контракте, переименование видно только в SQL.
- **Время только с часовым поясом.** Все даты — `timestamptz` (Postgres хранит их в UTC).
  Тип `AwareDateTime` отклоняет `datetime` без пояса ещё до запроса: иначе Postgres молча
  приписал бы ему пояс сервера.
- **Enum — `varchar` + `CHECK`**, а не нативный тип Postgres: новые значения добавляются
  обычной миграцией. Правила контракта (у встречи есть начало, конец позже начала) продублированы
  в `CHECK` — база не примет некорректную запись даже в обход сервисов.
- **Изоляция пользователей** — на уровне запросов: каждый запрос сервисов фильтрует по `user_id`,
  оба индекса начинаются с `user_id`.
- **Синхронный psycopg 3** (`postgresql+psycopg://`): проще код и тесты, FastAPI выполняет
  синхронные эндпоинты в пуле потоков. Psycopg 3 умеет и async, если понадобится.
- **Векторов в `records` нет.** Векторы названий — в таблице `text_embeddings` модуля поиска
  (миграция `0005`, [`search.md`](search.md)): вектор на текст, а не на запись. Расширение
  `vector` включает миграция `0001`.

## Сервисы

Чистая бизнес-логика без HTTP: её вызывают агент (tools) и API. Принимают и возвращают только
Pydantic-модели контрактов. Сессия БД передаётся явным аргументом `db` первым параметром.
Ошибки бизнес-правил — `ActionResult(ok=False, error=...)`, не исключения: агент передаёт текст
ошибки LLM, API не отдаёт 500.

### Транзакции: один коммит на реплику

Сервисы записей и состояния **не делают `commit`** — только `add` / `flush` в переданную сессию.
Коммитит маршрут `POST /api/chat` один раз, после того как агент обработал реплику; любое
исключение — `rollback` всего, что сделала реплика, и 500 (`docs/decisions.md`, «Доступ к БД»).
Так изменение записи и состояние разговора с прежними значениями для «верни» сохраняются вместе:
не бывает переноса, который нечем откатить.

- Сохранение записи идёт в точке сохранения (`begin_nested`): ошибка базы откатывает только эту
  запись (`ok=False`), остальное в транзакции реплики остаётся. Новые значения полей ставятся
  уже внутри точки сохранения: `begin_nested` сначала сбрасывает в базу всё накопленное в сессии,
  и ошибка заранее изменённой записи сломала бы транзакцию реплики (тест
  `test_failed_save_does_not_break_turn`).
- Строку нового гостя (`users`) зависимость пользователя коммитит сама, до реплики: гость не
  должен пропасть, если реплика упала.
- `GET /api/items` только читает — коммит не нужен.
- Агент сам не коммитит.

### Записи — `services/records.py`

**`create_record(db, user_id, action: CreateRecord) -> ActionResult`**

Проверки по порядку (`validate_create`, до обращения к базе):

| Правило | Результат |
|---|---|
| у `start` / `end` / `deadline` нет часового пояса | `ok=False` |
| встреча без `start` | `ok=False`, `missing=["start"]` |
| встреча, время не названо (`time_given=False`) | не сохраняется, `ok=False`, `missing=["start"]` — агент переспросит «На какое время?» |
| `end <= start` | `ok=False` |
| `start` или `deadline` в прошлом | `ok=False` |

- `all_day=True` — только если назван день, но не время (`start` задан, `time_given=False`):
  задача и напоминание «на весь день». Задача без даты («прочитать книгу») или только со сроком —
  `all_day=False`.
- «В прошлом» для `all_day` сравнивается по дням в поясе самой даты: «сегодня» без времени —
  не прошлое. Для записей со временем — `start < now − 1 минута` (`PAST_GRACE`): LLM считает
  время от момента запроса, проверка идёт после ответа модели, и «напомни через минуту»
  не должно отклоняться из-за этих секунд.
- **Точный дубль** — активная запись пользователя с тем же названием (без учёта регистра —
  `lower()` базы с обеих сторон) и тем же `start` — не создаётся: `ok=False`, `error`, существующая запись в `records` (`find_duplicate`).
- **Конфликт** — у встречи со временем: другие активные встречи пользователя, пересекающиеся по
  времени (`find_conflicts`). Встрече без `end` для проверки даётся 60 минут от `start` (и новой,
  и найденным); в запись это не пишется. Встречи «на весь день» не участвуют. Запись сохраняется,
  пересечения — в `ActionResult.conflicts`.
- При успехе: `ok=True`, `records=[созданная запись]`, `conflicts` — пересечения или пусто.

**`update_record(db, user_id, record_id, action: UpdateRecord, *, now) -> RecordChange`**

Запись уже найдена агентом по `TargetRef` (`record_id`); из `UpdateRecord` берутся только
меняемые поля, не равные `None`: `title`, `start`, `end`, `time_given`, `deadline`.

- Остальные поля не трогаются. `time_given=False` при новом `start` — «весь день», как при
  создании; `time_given` не передан — «весь день» остаётся прежним.
- У встречи с концом перенос начала без нового конца **сдвигает конец** на ту же величину —
  длительность сохраняется (иначе конец оказался бы раньше начала, и перенос не прошёл бы).
- Проверки — как при создании: пояс, конец позже начала, новая дата не в прошлом. Встреча без
  времени — `missing=["start"]`.
- Чужая или несуществующая запись — `ok=False`, «Запись не найдена.»
- У переносимой встречи — пересечения в `conflicts` (без неё самой).

**`set_status(db, user_id, record_id, status) -> RecordChange`** — `done` / `cancelled` / `active`.
Отменённая запись не удаляется, а пропадает из списков; `active` её возвращает.

**`RecordChange`** — `result: ActionResult` и `before: dict` — прежние значения изменённых полей
в JSON-виде, даты — в поясе пользователя (`{"start": "2026-10-22T15:00:00+03:00"}`).
«Весь день» в `before` записывается как `time_given`, статус — `{"status": "active"}`.
Агент кладёт `before` в `last_action.before`. При ошибке `before` пустой.

**`restore_record(db, user_id, record_id, before: dict) -> RecordChange`** — откат изменения:
полям возвращаются значения из `before`, который вернул `update_record`.

- Отдельный сервис нужен потому, что в `UpdateRecord` `None` значит «не менять»: пустое прежде
  поле через него не вернуть. Пример: задаче без срока поставили срок на пятницу —
  `before = {"deadline": null}`; `restore_record` срок убирает.
- «Не в прошлом» не проверяется: встречу перенесли с 10:00 на 12:00, «верни» сказали в 11:00 —
  запись возвращается на 10:00. Пояс и «конец позже начала» проверяются.
- Чужая запись или поле не из `title`, `start`, `end`, `deadline`, `time_given` — `ok=False`.

**Откат («верни»)**:

| Что откатываем | Чем |
|---|---|
| изменение | `restore_record(..., before)` |
| смену статуса | `set_status(..., RecordStatus(before["status"]))` |
| создание | `set_status(..., RecordStatus.CANCELLED)` |

Каждый вариант проверен тестом (`tests/test_backend03.py`).

**`list_records_for_period(db, user_id, action: ListRecords) -> ActionResult`**

- Записи пользователя, у которых `start` **или** `deadline` в `[date_from, date_to)` — правая
  граница не включается (контракт `agent-tools.md`): «сегодня» — до 00:00 завтра, и запись
  «на весь день» завтра в него не попадает. «Задачи на завтра» находят и задачи только со сроком.
- Отменённые (`cancelled`) не показываются; остальные статусы — показываются.
- Фильтр `types`, если передан. Сортировка по `coalesce(start, deadline)`.
- Ничего нет — `ok=True, records=[]`.
- `date_to=None` — без верхней границы; в конец добавляются активные записи без начала
  и срока через `list_undated_records`, с тем же фильтром пользователя и типов.

### Состояние разговора — `services/conversation.py`

| Функция | Что делает |
|---|---|
| `get_conversation_state(db, conversation_id, user_id)` | состояние существующего разговора, без создания: нет разговора → `None`. Чужой разговор → `ConversationAccessError` |
| `get_or_create_conversation_state(db, conversation_id, user_id)` | состояние из БД; для нового разговора создаёт пустое (`flush`, коммит — в маршруте). Чужой разговор → `ConversationAccessError` |
| `save_conversation_state(db, state)` | записывает в сессию (`flush`) `focus_record_id`, `shown`, `last_action`, `pending`, `pending_skipped`, `candidates`, `missing`, `awaiting`; коммит — в маршруте |
| `merge_pending(state, incoming)` | дописывает в черновик `pending` непустые поля из `incoming`, уже сохранённое не затирает; заполненные поля убирает из `missing` |
| `clear_pending(state)` | очищает `pending`, `missing`, `awaiting` после успешного действия |
| `forget_last_action_for_record(db, user_id, record_id)` | сбрасывает `last_action` во всех разговорах пользователя, где оно затрагивает запись (запись среди `record_ids`, в том числе у массового действия); остальное состояние не трогает. Без `commit`. Для кнопок `/api/items` (backend-05) |

Для загрузки фокуса агент использует `services.records.get_record(db, user_id, record_id)`:
возвращает `Record` либо `None`, фильтруя по ID записи и владельцу в SQL. ORM наружу не передаётся.

Сценарий уточнения: «поставь встречу с Иваном завтра» → `create_record` вернул `missing=["start"]` →
агент кладёт черновик в `pending`, `awaiting="answer"`, сохраняет → «в 14» →
`merge_pending(state, {"start": ..., "time_given": True})` → `create_record(pending)` →
`clear_pending` + `focus_record_id` = созданная запись → сохранить.

`merge_pending` — по паттерну livekit-booking-system (`context_manager._save`): берётся весь старый
черновик и поверх кладутся только непустые новые значения. Очистка вынесена в отдельную
`clear_pending`: в одном вызове слить и сразу очистить черновик нельзя.

## Миграции

```bash
cd backend
uv run alembic upgrade head          # создать / обновить схему
uv run alembic downgrade base        # откатить всё
uv run alembic check                 # модели совпадают с базой?
uv run alembic revision --autogenerate -m "что изменилось"   # новая миграция после правки models.py
```

| Ревизия | Что делает |
|---|---|
| `0001` | `CREATE EXTENSION IF NOT EXISTS vector` |
| `0002` | таблицы `records`, `conversation_states`, индексы и ограничения |
| `0003` | `conversation_states`: `shown`, `last_action`, `pending_skipped` — у существующих строк значения по умолчанию |
| `0004` | таблицы `users`, `auth_tokens`; `records.cancelled_at`. Уже существующие пользователи (по записям и разговорам) становятся гостями с последним запросом «сейчас»; у отменённых записей момент отмены — `updated_at` |
| `0005` | таблица `text_embeddings` модуля поиска (`search.md`) |

Автогенерированную миграцию нужно вычитать: в ней не должно быть ссылок на код приложения
(`db.models...`), имена ограничений оборачиваются в `op.f(...)`.

## Стартовый датасет — `services/bootstrap.py`

Копия 1000 записей из `backend/data/voice_assistant_events_1000.csv` — **только у демо-учёток**
(`docs/decisions.md`, «Датасет»; с backend-04), чтобы списки за период и поиск можно было
показать сразу. Гость и новая учётка начинают с пустого календаря. Загрузку вызывает
`services/demo_accounts.py` при создании и сбросе демо-учётки, в поясе Europe/Moscow.

**`bootstrap_user_data(db_session, user_id, timezone_str) -> int`** — возвращает число
добавленных записей (0, если у пользователя записи уже есть). Неизвестный пояс —
`ZoneInfoNotFoundError`, некорректное имя (пустое, с `..`) — `ValueError`, оба до обращения к базе.

**Транзакция.** Функция сама завершает транзакцию переданной сессии: `commit` и когда загрузила,
и когда пропустила; при ошибке — `rollback` и исключение дальше. Поэтому вызывать её первой в
запросе, до своих изменений, — дальше сессией можно пользоваться как обычно.

| Правило | Как сделано |
|---|---|
| Часовой пояс | время из CSV — локальное время пользователя: «10:00» остаётся 10:00 в его поясе (`datetime.combine(date, time, tzinfo=ZoneInfo(tz))`), в базе — `timestamptz` |
| Тип | `detect_type(text)`: «Напомнить …» → `reminder`; первое слово «Встреча» / «Созвон» / «Демо» / «Планёрка» или «планёрк…» в любом месте («Провести планёрку …») → `meeting`; остальное → `task`. «Отправить итоги встречи …», «Подготовиться к встрече …» — `task`: «встреча» не первое слово |
| Статус | событие раньше момента импорта → `done`, иначе `active` |
| Поля | дата и время CSV → `start`, `all_day = false` (время в CSV есть всегда), `deadline` пустой |
| Идемпотентность | есть хоть одна запись у `user_id` → импорт пропускается |
| Изоляция | все записи — строго переданному `user_id` |
| Скорость | один запрос `INSERT … VALUES (…), (…)` на все строки (SQLAlchemy `insert(Record).values([...])`), ~0,5 с на 1000 записей |

**Одновременные загрузки.** Два процесса могут загружать датасет одному пользователю
одновременно (например, два старта бэкенда создают одну демо-учётку). Чтобы датасет не
загрузился дважды, импорт берёт транзакционную
блокировку Postgres по `user_id` (`pg_advisory_xact_lock`) — второй запрос ждёт первого и видит,
что записи уже есть. Блокировка снимается с концом транзакции — в том числе при ошибке импорта.
Оба случая проверяют тесты: 4 одновременных импорта одному пользователю → данные загружены один
раз; битый CSV → исключение, записей нет, блокировка свободна.

Распределение типов в датасете: `task` 761, `meeting` 186, `reminder` 53 (тест на полном CSV).
Дубли текста (376 уникальных на 1000 строк) — разные события с разными датами, загружаются все.

## API — `api/`, `main.py`

Маршруты FastAPI поверх сервисов; бизнес-логики в `api/` нет. Swagger — `/docs`.
Запуск: `cd backend && uv run uvicorn main:app --reload`.

| Файл | Что внутри |
|---|---|
| `main.py` | приложение FastAPI, CORS, подключение роутеров; при старте — демо-учётки и чистка |
| `api/deps.py` | пользователь (учётка по токену или гость по `X-User-Id`), разбор часового пояса |
| `api/auth.py` | `/api/auth/*` — регистрация, вход, выход, `me`; лимит попыток входа |
| `api/chat.py` | `POST /api/chat` |

| `api/health.py` | `GET /health` |

### Пользователь — учётка или гость

Зависимость `get_current_user_id` (`api/deps.py`) — у всех `/api/*`, кроме `/api/auth/*`:

- **Есть `Authorization: Bearer <token>`** — это учётка; `X-User-Id` не читается и не выдаётся.
  Токен неизвестный, отозванный или истёкший — **401** (молча в гостя не переводим: интерфейс
  решает сам). Подробнее — «Учётки и вход».
- **Токена нет — гость по `X-User-Id`:**
  - фронтенд хранит UUID в localStorage и присылает его в заголовке каждого запроса;
  - нет заголовка или он пустой → новый `uuid4()` **в заголовке ответа `X-User-Id`** (CORS
    открывает его фронтенду через `expose_headers`); новый гость — с **пустым** календарём;
  - не UUID → **400**: ошибка клиента, сервер не подменяет id молча;
  - id учётки без токена → **401**: иначе знающий id входил бы в учётку без пароля.
- Строка гостя в `users` заводится при первом запросе и коммитится сразу; время последнего
  запроса обновляется не чаще раза в час — для чистки через 30 дней.

### `POST /api/chat`

Тело — `ChatRequest`, ответ — `ChatResponse` (`docs/contracts/api.md`).

- `conversation_id = null` → новый разговор, сервер присваивает id и создаёт состояние разговора.
- Чужой или несуществующий `conversation_id` → **404**: разговоры создаёт только сервер.
- Неизвестный или пустой `timezone` → **422** с понятным текстом.
- `llm_config` принимается и нигде не сохраняется и не логируется.
- Сервисы синхронные — вызываются через `asyncio.to_thread` (`docs/decisions.md`).

Реплику обрабатывает агент: `process_user_turn(db, user.id, conversation_id, req.text, zone,
req.llm_config)`.

**Порядок транзакции** (один коммит на реплику):

1. Пользователь: новый гость заводится в `users` (коммитит сама зависимость, до реплики).
2. Проверки запроса: пояс, разговор.
3. Агент обрабатывает реплику: изменения записей и состояние разговора — в одной транзакции.
4. Успех → `commit`. Любое исключение → `rollback` всего, что сделала реплика, и 500.

### `GET /api/items`

| Параметр | Смысл |
|---|---|
| `from`, `to` | **обязательные**: период `[from, to)`, ISO 8601 со смещением (`+` в URL кодируется как `%2B`). Обязательны, как `date_from` / `date_to` у `ListRecords` в контракте; без них — 422 |
| `type` | фильтр, можно несколько: `?type=meeting&type=task` |
| `tz` | IANA-пояс пользователя (по умолчанию Europe/Moscow): даты в ответе — в этом поясе |
| `include_undated` | `true` — добавить в конец активные записи **без даты** (блок «Без срока», FEATURES P1 №14). По умолчанию `false` |

Ответ — `list[Record]`, по времени. Записи без даты (с `include_undated=true`) — в конце, у них
`start` и `deadline` пустые: по этому фронтенд отделяет их в свой блок. Фильтр `type` действует
и на них; выполненные и отменённые без даты не показываются (`services.list_undated_records`).

Нет `from` / `to`, `to <= from`, дата без пояса, неизвестный или пустой `tz` → 422.

### `GET /health`

`SELECT 1` в базе: `{"status": "ok", "db": "connected"}` (200) или
`{"status": "error", "db": "unavailable"}` (503) — в том числе когда не задан `DATABASE_URL`.
Таймаут подключения к базе — 5 с (`db/session.py`): недоступная база даёт 503, а не зависание.

### CORS

Разрешены `https://gorky.bond`, `https://www.gorky.bond`, `http://localhost:3000`,
`http://localhost:5173` (и те же с `127.0.0.1`). Переопределяется переменной окружения
`CORS_ORIGINS` (через запятую) без изменения кода. Заголовки запроса разрешены все
(`allow_headers=["*"]` — Starlette отвечает списком из запроса), в том числе `Authorization`.

## Записи из интерфейса — кнопки `/api/items`

Контракт — [`api.md`](../contracts/api.md), «Записи из интерфейса» (backend-05). Кнопки в карточке
и календаре делают то же, что агент голосом, — теми же сервисами записей и с теми же проверками,
но без LLM. Схемы тел — `schemas/items.py` (`CreateItem`, `UpdateItem`, `SetItemStatus`),
маршруты — `api/items.py`.

| Маршрут | Сервис | Ответ |
|---|---|---|
| `POST /api/items` (`CreateItem`) | `create_record` | `201 ActionResult` |
| `PATCH /api/items/{id}` (`UpdateItem`) | `update_record` | `200 ActionResult` |
| `POST /api/items/{id}/status` (`SetItemStatus`) | `set_status` | `200 ActionResult` |

- **Ответ** — `ActionResult`, как у чата: в `records` одна запись, у встречи в `conflicts` —
  пересечения (запись всё равно сохраняется). Даты — в поясе `tz` (параметр запроса, по
  умолчанию Europe/Moscow), как у `GET /api/items`.
- **Пользователь** — та же зависимость `get_current_user_id`: учётка по токену или гость.
- **`UpdateItem` → `update_record`.** Адаптер в маршруте: `UpdateRecord(target=TargetRef(), …)` —
  сервису нужна только уже найденная запись (`record_id`), цель он не читает. Сигнатура сервиса
  не менялась. `shift_minutes` наружу не отдаётся: кнопка всегда знает новое время. `null` —
  «не менять»: убрать дату или срок этим эндпоинтом нельзя, как и голосом. Перенос начала
  встречи без нового конца сохраняет длительность — это делает сам `update_record`.
- **Удаление мягкое:** «Удалить» — `status = cancelled`, запись пропадает из `GET /api/items`;
  «Вернуть» — `status = active` по тому же `id`. Насовсем её стирает только чистка через 30 дней.

### Ошибки

| Код | Когда |
|---|---|
| 400 | `X-User-Id` не UUID |
| 401 | токен учётки недействителен |
| 404 | записи нет или она чужая — «Запись не найдена.» (проверка до сервиса) |
| 422 | отказ сервиса (`ok=False`) — `detail` из `ActionResult.error`: дата в прошлом, конец раньше начала, встреча без начала или без времени, точный дубль, нечего менять |
| 422 | тело не по схеме — тоже одной строкой, по полям: «Нужно название записи.», «Тип записи — task, meeting или reminder.», «Начало — дата и время ISO 8601 с часовым поясом…», «Статус — active, done или cancelled.»; несколько ошибок — через пробел. Обработчик — `api/errors.py` |

### Транзакция

Один запрос — одна транзакция (`_in_one_transaction`): сервисы и сброс `last_action` только пишут
в сессию, маршрут коммитит при успехе. Отказ сервиса (422) и любая ошибка — откат всего, что
запрос успел сделать: полусохранённых изменений нет (тест `test_error_mid_request_saves_nothing`).

### Ручная правка и чат

Изменение кнопкой в состояние разговора **не пишется**, но после успешного изменения или смены
статуса `forget_last_action_for_record` сбрасывает `last_action` во всех разговорах пользователя,
где оно затрагивает эту запись (у массового действия — запись среди `record_ids`; поиск —
JSONB `last_action -> 'record_ids' @> '["<id>"]'`). Иначе голосом «перенеси на пятницу», кнопкой —
на субботу, «верни» в чате откатило бы на четверг поверх ручной правки. Теперь «верни» честно
отвечает «Нечего возвращать». Номера на экране (`shown`), фокус и черновик не трогаются.
Создание кнопкой `last_action` не сбрасывает: новую запись никакое прошлое действие не затрагивает.

## Учётки и вход — `/api/auth/*`

Контракт — [`api.md`](../contracts/api.md), «Учётки и вход»; решение — `decisions.md`,
«Пользователи», «Датасет». Вход по желанию: без него страница работает гостем.

| Файл | Что внутри |
|---|---|
| `api/auth.py` | маршруты, тексты ошибок, лимит попыток входа |
| `services/accounts.py` | гость, учётка, пароли, токены |
| `services/demo_accounts.py` | демо-учётки: разбор `DEMO_ACCOUNTS`, создание, сброс |
| `services/retention.py` | чистка по сроку хранения |
| `scripts/demo_accounts.py`, `scripts/cleanup.py` | команды для сервера |

### Таблицы

**`users`** — все пользователи. Гость — строка без логина, учётка — с логином и паролем.

| Колонка | Тип | Правила |
|---|---|---|
| `id` | uuid | PK; тот же `user_id`, что у записей и разговоров (`Account.id`) |
| `login` | varchar(32) | у гостя пусто; уникален **без учёта регистра** (индекс `lower(login)`) |
| `password_hash` | text | argon2; есть ровно тогда, когда есть логин |
| `is_demo` | boolean | демо-учётка с датасетом; только у учёток |
| `created_at` | timestamptz | `now()` |
| `last_seen_at` | timestamptz | последний запрос гостя, обновляется не чаще раза в час |

**`auth_tokens`** — выданные токены: `token_hash` (SHA-256, PK), `user_id` (FK → `users`,
`ON DELETE CASCADE`), `created_at`, `expires_at`.

**Внешних ключей от `records` и `conversation_states` к `users` нет.** Сервисы и их тесты
создают записи по `user_id` без строки пользователя (так устроены все тесты записей и агента),
а удаление гостя и так делает чистка, явно по `user_id`. Строка пользователя заводится
зависимостью `get_current_user_id` до любой записи, поэтому у данных из API она есть всегда.

### Токен — случайная строка в таблице, а не JWT

- `secrets.token_urlsafe(32)`, в базе — только его **SHA-256**. Токен длинный и случайный —
  по хешу его не подобрать; медленный хеш нужен паролям, которые придумывают люди.
- Срок жизни — **30 дней** от входа. Каждый вход — новый токен: ноутбук и телефон жюри
  работают одновременно, выход на одном не выкидывает другой.
- Выход — удаление строки: после него токен не принимается (требование контракта).
- **Почему не JWT:** контракт требует, чтобы после выхода токен не принимался, — значит, для JWT
  всё равно нужна таблица отозванных токенов или версия у пользователя, плюс секрет подписи в
  `.env`. Таблица токенов проще и даёт то же: один запрос к базе на вызов для прототипа не
  проблема.

### Пароли — argon2

Библиотека `argon2-cffi`, параметры по умолчанию (argon2id, соль у каждого хеша). Пароль и токен
нигде не хранятся открытым текстом и не пишутся в лог. Вход с несуществующим логином тоже
проверяет пароль (по служебному хешу) — по времени ответа не видно, есть ли такой логин.

### Маршруты и ошибки

| Маршрут | Ответ | Ошибки |
|---|---|---|
| `POST /api/auth/register` (`Credentials`) | `201 AuthResponse` — учётка создана, вход выполнен | 409 логин занят, 422, 429 |
| `POST /api/auth/login` (`Credentials`) | `200 AuthResponse` | 401 «Неверный логин или пароль.» — одним текстом, 422, 429 |
| `POST /api/auth/logout` с токеном | 204, токен удалён | 401 |
| `GET /api/auth/me` с токеном | `Account` | 401 |

- Ошибки — `{"detail": "<текст для пользователя>"}`. У `/api/auth/*` и 422 — текстом
  («Логин — от 3 до 32 символов…», «Пароль — от 8 до 128 символов.»), а не списком ошибок
  FastAPI (обработчик `credentials_validation_handler`, подключён через `api/errors.py`).
  Так же строкой отвечают кнопки записей; остальные маршруты (и `GET /api/items`) — на 422
  как раньше, списком.
- 401 по токену — с заголовком `WWW-Authenticate: Bearer`.

### Лимит попыток входа

- **10 неудачных попыток за 15 минут на пару «логин + IP»** (логин без учёта регистра) → 429 с
  `Retry-After`, и с верным паролем тоже, пока окно не прошло. Удачный вход счётчик сбрасывает.
- Только по логину нельзя: чужой человек десятью неверными паролями закрыл бы вход в учётку
  жюри прямо во время показа (пароль жюри публичный). IP — из `X-Real-IP`, его ставит Nginx
  (`proxy_params`, `docs/infra.md`) и клиент подделать не может: бэкенд открыт только на
  127.0.0.1. Без Nginx (локально) — адрес соединения. `X-Forwarded-For` не годится: Nginx
  дописывает адрес в конец, а начало списка присылает сам клиент.
- **30 запросов в минуту на вход и регистрацию с одного IP** → 429: хеш пароля нарочно
  медленный, поток таких запросов занял бы единственное ядро сервера, а массовая регистрация
  засоряла бы базу. По IP, а не на всех вместе: общий счётчик дал бы любому закрыть вход всем,
  в том числе жюри на показе.
- В памяти процесса — бэкенд один; после перезапуска счётчики обнуляются.

### Демо-учётки

- Список — `DEMO_ACCOUNTS` в `.env` (и в `environment` бэкенда в `docker-compose.yaml`),
  **JSON-объект «логин → пароль»** в одинарных кавычках:
  ```
  DEMO_ACCOUNTS='{"jury": "пароль-жюри", "denis": "пароль-дениса"}'
  ```
  Логин и пароль — по правилам `Credentials`; в пароле можно любые символы. Ошибка в
  переменной — понятный текст в логе при старте (какая учётка и что не так, без пароля).
- **Создание недостающих — само при каждом старте бэкенда** (`main.py`, `lifespan`): и на
  сервере (контейнер стартует при деплое после миграций), и при локальном
  `uv run uvicorn main:app`. Новой демо-учётке загружается датасет (~1 с). Повторный старт
  ничего не дублирует; если пароль в `.env` поменяли — обновляет хеш. Демо-учётка без
  записей (загрузка датасета упала после создания учётки) получает датасет при следующем старте.
- Логин из списка занят обычной учёткой → она не трогается, предупреждение в логе.
- Учётка, убранная из `DEMO_ACCOUNTS`, остаётся в базе как была.
- **Сброс — вручную, перед показом** (через API нельзя: пароль жюри публичный):
  ```bash
  # на сервере
  docker compose exec backend python -m scripts.demo_accounts --reset jury
  docker compose exec backend python -m scripts.demo_accounts --reset-all
  # локально, из backend/
  uv run python -m scripts.demo_accounts --reset jury
  ```
  Удаляет записи и разговоры учётки и загружает датасет заново; токены не трогает — жюри
  остаётся в учётке. Остальных пользователей не трогает.

### Срок хранения — 30 дней

`services/retention.py`, `cleanup(db, now=...)`:

| Что | Когда удаляется |
|---|---|
| гость (строка `users` без логина) вместе с записями и разговорами | нет запросов 30 дней (`last_seen_at`) |
| запись любого пользователя | отменена больше 30 дней назад (`cancelled_at`) |
| токен входа | истёк |
| учётки и демо-учётки | никогда |

- **Момент отмены** ставит `set_status` (`services/records.py`) — единственный путь отмены, в том
  числе массовой отмены агентом: `cancelled` → `cancelled_at = now`; повторная отмена время не
  меняет; `active` и `done` его очищают («Вернуть» — запись снова живёт без срока).
- **Запуск — в процессе бэкенда:** при старте и потом раз в 6 часов (`main.py`). Отдельный cron на
  сервере не нужен, бэкенд один. Вручную: `python -m scripts.cleanup`.
- Чистка — одна транзакция, повторяемая: второй запуск подряд ничего не находит.

## Распознавание речи — `POST /api/stt`

Контракт — [`api.md`](../contracts/api.md), «Распознавание речи». Голос идёт в два шага:
запись → `POST /api/stt` → текст → обычный `POST /api/chat`. Агент и контракт чата для голоса
не меняются; ошибки распознавания остаются в `/api/stt` и до агента не доходят.

| Файл | Что внутри |
|---|---|
| `api/stt.py` | маршрут: порядок проверок, коды ответов, значения лимитов |
| `stt/audio.py` | формат записи и её длительность — из заголовков контейнера, без ffmpeg |
| `stt/client.py` | вызов Gemini, разбор ответа |
| `stt/rate_limit.py` | лимит частоты на пользователя, в памяти процесса |

### Сервис и модель

- **Gemini, нативный API** `POST https://generativelanguage.googleapis.com/v1beta/models/{STT_MODEL}:generateContent`,
  ключ — в заголовке `x-goog-api-key` (не в адресе, чтобы не попасть в логи). Запись уходит
  в теле запроса (`inlineData`, base64) как есть: без перекодировки и без записи на диск.
- **Почему нативный, а не OpenAI-совместимый адрес агента:** совместимый адрес не принимает
  запись из браузера — проверено живьём (2026-10-26, `gemini-3.5-flash-lite`, запись Chrome
  `voice.webm` через `input_audio`): `400 INVALID_ARGUMENT: Invalid audio format "webm" for audio
  generation. Valid formats are: [wav, mp3]`. Перекодировать в wav/mp3 задача не разрешает
  (без ffmpeg на сервере). У нативного API `audio/webm` и `audio/m4a` — в списке форматов.
- Новых библиотек нет: запрос через `httpx` (он и так стоит — от него зависит `openai`; теперь
  указан в зависимостях явно). Добавлен только `python-multipart` — без него FastAPI не
  принимает файлы.
- `audio/mp4` (Safari) отправляется как `audio/m4a`: так Gemini называет AAC в контейнере MP4,
  `audio/mp4` в его списке нет.
- Промпт: расшифровать дословно, на русском, без пересказа; если речи нет — пустой текст.
  Ответ — JSON по схеме `{"text": ...}` (`responseSchema`), `temperature = 0`: так «речи нет»
  не спутать с пояснением модели вроде «в записи тишина».
- Переменные окружения (в `.env.example` и `docker-compose.yaml`), отдельно от `LLM_*`;
  `llm_config` пользователя на распознавание не влияет:

  | Переменная | Смысл |
  |---|---|
  | `STT_API_KEY` | ключ Gemini; может совпадать с `LLM_API_KEY`. Пусто — 503 |
  | `STT_MODEL` | модель Gemini, принимающая аудио, напр. `gemini-3.5-flash-lite`. Пусто — 503 |
  | `STT_THINKING_LEVEL` | необязательно: уровень «обдумывания» (`thinkingConfig.thinkingLevel`), напр. `minimal`, `low`. Пусто — в запросе не передаётся, модель работает со своим уровнем по умолчанию |

- **Почему `STT_THINKING_LEVEL` пустой по умолчанию:** допустимые уровни у моделей Gemini
  разные (`minimal` есть у `gemini-3.5-flash-lite`, но не у `gemini-3.8-flash`). Зашитое
  значение сломало бы распознавание при смене модели — Gemini ответил бы ошибкой, `/api/stt` — 503.
  Поэтому уровень меняется вместе с моделью, в `.env` сервера, без правки кода.
- Таймаут запроса к Gemini — 25 с, без повторов: повтор удвоил бы ожидание пользователя.

### Порядок проверок и коды

| Шаг | Код |
|---|---|
| `X-User-Id` не UUID | 400 |
| токен учётки недействителен; id учётки в `X-User-Id` без токена | 401 |
| больше 15 запросов за 60 с от пользователя или 120 за 60 с от всех вместе | 429 + `Retry-After` |
| поле `audio` отсутствует или пустое; `Content-Type` не из списка; начало файла не совпадает с форматом | 415 |
| файл больше 10 МБ; запись длиннее 30 с | 413 |
| запись короче 0,3 с | 422 — без запроса к провайдеру |
| Gemini: нет ключа или модели, сеть, таймаут, любой ответ не 200 | 503 |
| Gemini вернул пустой текст (тишина, шум) или ничего не вернул | 422 |

Ответ с ошибкой — `{"detail": "<текст для пользователя>"}`, без трассировки. Подробности ошибки
провайдера — только в лог сервера.

`Content-Type` берётся из части `audio` без параметров: `audio/webm;codecs=opus` → `audio/webm`.
Отсутствие поля — тоже 415, а не стандартная ошибка валидации FastAPI 422: по контракту 422
значит «не расслышал».

### Длина записи — по длительности

Размер не годится как мера длины: при низком битрейте 1 МБ — это минуты речи, и лимит
провайдера можно было бы тратить длинными записями. Поэтому длительность читается из
заголовков контейнера (`stt/audio.py`):

| Формат | Откуда длительность |
|---|---|
| `audio/webm` (Chrome) | метки времени блоков: Chrome пишет запись потоком, общей длительности в файле нет |
| `audio/mp4` (Safari) | фрагменты `moof`: у записи MediaRecorder общий заголовок обычно пустой |
| `audio/ogg` | позиция последнего сэмпла в последней странице |
| `audio/wav` | размер данных / байт в секунду |

- Предел — **30 с ровно**, как в контракте: длиннее хоть на долю секунды — 413. Фронтенд
  останавливает запись на 29,5 с (`MAX_RECORDING_MS`, `frontend/src/lib/recorder.ts`):
  длительность файла может отличаться от таймера на странице на десятки миллисекунд.
- Если длительность не прочиталась (повреждённый файл) — запасное правило по размеру:
  не больше 30 с × 320 кбит/с = 1,2 МБ. Запись Chrome (opus, 128 кбит/с) за 30 с — около 0,5 МБ.
- Общий предел файла — 10 МБ (30 с несжатого WAV 48 кГц стерео — около 5,8 МБ).
- Starlette по умолчанию сбрасывает файл больше 1 МБ во временный файл на диске — порог
  поднят до 10 МБ (`MultiPartParser.spool_max_size`), запись остаётся в памяти.
- Разбор заголовков — синхронный цикл по файлу, поэтому идёт в потоке (`asyncio.to_thread`):
  пока он считает, сервер отвечает остальным.
- Числам из файла разбор верит не больше, чем помещается в сам файл: число сэмплов в `trun`
  (MP4) ограничено размером бокса. Иначе файл в 104 байта с count = 4 млрд держал бы сервер
  в цикле десятки минут (замер на исходной версии: 10 млн сэмплов — 2,8 с).

### Частота — 15 запросов за 60 секунд на пользователя, 120 на всех

Скользящее окно в памяти процесса (бэкенд один). Одна реплика — запись и 2–5 с распознавания,
так что живой разговор — до 10–15 реплик в минуту; 15 — верхняя граница живого разговора.
Отклонённые запросы окно не продлевают.
Пользователь без `X-User-Id` каждый раз получает новый id, и лимит на пользователя обходится
сменой id. Поэтому есть общий предел на весь сервер — 120 запросов за 60 секунд: он защищает
серверный ключ от одного посетителя, который шлёт запросы без заголовка. 120 — восемь человек,
которые говорят без пауз; столько одновременно на демо не бывает. Запрос, отклонённый лимитом
пользователя, общий предел не расходует.

### Проверено

- Тесты без сети (`tests/test_stt.py`): успешный ответ для webm, mp4, ogg, wav; каждый код
  ошибки; разбор ответа Gemini; запрос к Gemini (адрес, ключ в заголовке, формат). Записи
  собираются в самих тестах — минимальные контейнеры в том виде, как их пишет MediaRecorder:
  аудиофайлы в репозиторий не коммитим (`docs/dev-guide.md`).
- Длительность сверена с `ffprobe` на записях MediaRecorder из Chromium (webm и mp4, 2 и 31 с)
  и на файлах ffmpeg (ogg opus/vorbis, обычный и фрагментированный mp4, wav).
- Путь «браузер → `/api/stt`» с подменённым Gemini: запись MediaRecorder в Chromium
  (`audio/webm;codecs=opus`, `audio/mp4;codecs=opus`) отправлена `fetch` + `FormData` с
  `localhost:5173` — 200, CORS и `X-User-Id` работают; короткая запись — 422.
- **Живьём, локально (2026-10-26):** запись фразы в Chrome на компьютере (`audio/webm;codecs=opus`,
  ~100 КБ) → бэкенд → Gemini `gemini-3.5-flash-lite` с ключом команды → **200** за 5,1 с,
  распознанный текст вернулся. Формат из браузера Gemini принимает без перекодировки.
- **Не проверено живьём:** запись с телефона (Safari, `audio/mp4`) — на стенде после деплоя;
  пустая запись (тишина) → 422 — покрыто тестами с подменённым Gemini.
- **OpenAI-совместимый адрес Gemini** с записью Chrome (`webm`) — **400**, принимает только
  wav и mp3 (см. «Сервис и модель»).
- **Повреждённая запись** (настоящий заголовок WebM из Chrome, вместо звука — случайные байты):
  Gemini отвечает `400 INVALID_ARGUMENT: Request contains an invalid argument.` — общий текст
  без указания на аудио, как и при других ошибках запроса. Отличить «плохую запись» от ошибки
  настройки по нему нельзя, поэтому ответ — 503, подробности — в логе сервера.

## Внешний календарь

Задача [calendar-01](../tasks/calendar-01-vneshniy-kalendar.md), контракт — [`api.md`](../contracts/api.md), «Внешний календарь (Google)». Решения этапа 1 утверждены техлидом 28.10.2026.

### Calendar API, а не MCP

У Google есть официальный удалённый MCP-сервер календаря (`calendarmcp.googleapis.com/mcp/v1`), но в статусе Developer Preview — только участникам программы предпросмотра Google Workspace ([документация](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server)). MCP придуман, чтобы инструменты вызывала модель; у нас в Google ходит наш код после успешной операции сервиса, и MCP был бы прослойкой: наш код → MCP-сервер → Calendar API. Поэтому — Calendar API напрямую, официальными `google-auth` и `google-api-python-client`. Вызовы синхронные, как сервисы.

### Направление и что уходит в Google

Только наши записи → Google. Двусторонняя синхронизация потребовала бы решать, чья правка главнее, и встраивать события Google в пересечения, «верни» и номера на экране; при риске OAuth (ниже) это не окупается. События из Google у нас не показываются — следующий шаг, если будет время, «только для чтения».

| Наша запись | Событие в Google |
|---|---|
| Встреча со временем | с началом и концом; без конца — час, как в проверке пересечений |
| Напоминание со временем | 15 минут, уведомление в момент начала |
| Задача со временем | 30 минут |
| «На весь день» | на весь день |
| Задача только со сроком | на весь день в день срока, «Срок: {название}» |
| Без даты | не уходит |
| Отмена / «верни» | событие удаляется / восстанавливается |
| Выполнено | остаётся, к названию — «✓» |

**Первая выгрузка:** при подключении в Google уходят записи с датой в ближайшие 2 недели от сегодня; остальные — когда их создают или меняют у нас. У демо-учётки 1000 записей датасета: выгрузка всех заняла бы минуты внутри возврата из Google и не нужна для показа.

**Без дублей:** id события в Google — наш id записи (UUID без дефисов; Calendar API принимает id, заданный клиентом). Повтор создания — «уже есть» → обновление.

### Синхронизация и транзакция реплики

Вызов Google — после коммита реплики, не внутри транзакции: сбой или медленный Google не откатывает запись и не держит базу. Попытка сразу, с таймаутом 3 с; не вышло — запись помечается «ждёт», догоняет при следующем запросе пользователя (без отдельного планировщика). Доступ отозван (`invalid_grant`) — подключение в состоянии «ошибка», ассистент и «Мои дела» работают как без Google.

### OAuth и показ жюри

Чувствительные разрешения календаря (например, `calendar.events`) ограничены ([справка Google](https://support.google.com/cloud/answer/15549945)):
- в статусе **Testing** входят только внесённые вручную тестовые пользователи (до 100), доступ истекает через 7 дней — жюри не войдёт;
- в статусе **In production** без верификации входит любой аккаунт через экран «приложение не проверено» («Дополнительно → Перейти»), предел — 100 новых пользователей за всё время проекта, 7-дневного срока нет.

**Проверено в Cloud Console 28.10.2026:** `calendar.app.created` — **нечувствительное** (Data Access → «Your non-sensitive scopes»), `calendar.events` — чувствительное. Поэтому берём только `calendar.app.created`: доступ лишь к календарям, которые создало приложение. Предупреждения «приложение не проверено» нет, верификация не нужна, предела в 100 пользователей нет — жюри подключает свой Google без лишних экранов.

Следствие: записи уходят не в основной календарь пользователя, а в **отдельный календарь «Голосовой ассистент»**, который приложение создаёт при подключении (id календаря хранится у подключения; удалили в Google — при следующей синхронизации создаётся заново). Рабочие события пользователя приложение не видит и не трогает.

Статус приложения — **In production** (в Testing доступ истекает через 7 дней и только у внесённых вручную пользователей). Запасной путь для демо — показ на аккаунте команды.

Проект в Google Cloud создаёт Илья, техлид — второй владелец. Ключи — в `.env`:

| Переменная | Что |
|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | OAuth-клиент «Web application» |
| `GOOGLE_REDIRECT_URI` | `https://gorky.bond/api/calendar/google/callback` (локально — `http://localhost:8000/…`) |
| `GOOGLE_TOKEN_KEY` | ключ шифрования refresh-токенов в базе |

Токены хранятся только на сервере, refresh-токен — зашифрованным; в браузер и в логи не попадают.
