# Агент

## Подготовка запроса

`process_user_turn` получает IANA-пояс из `ChatRequest.timezone`, создаёт один aware
`now` и использует его для календаря, локализации инструментов и ответа.
Необязательный именованный параметр `now` подставляют автотесты (agent-08: «сейчас» —
среда 21.10.2026 10:00 по `Europe/Moscow`); без него берётся текущее время. Тот же `now`
уходит в модель, в описания инструментов и в сервис `create_record` (`execute(..., now=now)`):
проверка «дата в прошлом» считает от того же момента, что и модель.

`build_compact_system_prompt` находится в `agent/system_prompt.py`,
`get_agent_tools` и `localize_tools` — в `agent/tools.py`.

Промпт содержит 15 строк: роль, время, пояс, календарь двух недель и общие правила.
Начало недели — понедельник. Даты и границы периодов описаны преимущественно в полях
`backend/schemas/actions.py`. `localize_tools` глубоко копирует схемы и заменяет
`{ISO_EXAMPLE}` только в `description`, включая вложенные `$defs`.
Базовые схемы и результаты других запросов не меняются.

`get_action` отправляет ровно два сообщения: system с актуальным состоянием и user
с текущей репликой. История сообщений не отправляется. Один вызов
`chat.completions.create`, `tool_choice="required"`, ровно один tool call.
Имя и JSON-аргументы проверяются через `LLMAction.model_validate`.
Пустой/неизвестный вызов или нарушение схемы — `ActionParseError`.

## Порядок обработки реплики (agent-06)

1. Загрузить состояние с проверкой владельца разговора.
2. Если есть ожидание и вся нормализованная реплика совпадает с фразой отказа,
   очистить черновик, признак пропуска, кандидатов и ожидание. Сохранить один раз,
   ответить «Хорошо, не ставлю» / «Хорошо, ничего не меняю». LLM не вызывается.
   Ждём выбора или подтверждения (`choice`, `confirm`), а реплика — «номер N»: действие из
   `pending` над N-й записью из кандидатов, LLM не вызывается (раздел «Быстрые ответы»).
3. Последовательно загрузить доступные записи из `shown[:10]`, фокуса и первых трёх
   записей последнего действия. Повторяющиеся ID читаются один раз, всегда с `user_id`.
   Недоступный фокус снимается; пропуски в показанном списке сохраняют свои номера.
4. Собрать компактный контекст и вызвать модель.
5. Ответ на уточнение создания дополняет только ожидаемые поля дат; для `start`
   также `time_given`. Название, тип и остальные заполненные значения сохраняются.
   Слияние непустых значений выполняет `merge_pending`; полноту проверяет сервис.
6. Исполнить действие через `execute` (`ask_user` обрабатывается без сервиса).
7. Вызвать `update_state`, сохранить состояние один раз и сформировать ответ шаблоном.
   При первом отвлечении от черновика добавить напоминание о незавершённом действии.

Фразы отказа: «не надо», «забудь», «отмена», «проехали», «забей», «неважно»,
«отбой», «стоп». Нормализация: NFKC, регистр, пунктуация и пробелы.
Сверяется вся фраза: «Отмени встречу с Иваном» и «не надо отменять» не являются отказом.

## Интерфейс для agent-07

Общий переход состояния — в `backend/agent/state.py`:

```python
from agent.state import update_state

state = update_state(state, action, result, before=before)
```

Сигнатура: `update_state(state, action, result, *, before=None) -> ConversationState`.

- `action` — конкретная модель действия; обёртка `LLMAction` также принимается.
- `result` — `ActionResult`; только для `AskUser` можно передать `None`.
- `before` — список словарей с прежними значениями записей ДО изменения/смены статуса,
  в порядке `result.records`. Функция делает глубокую копию. Создание всегда хранит
  `before=[]`; при нескольких созданиях `record_ids` содержит все созданные записи.
- Функция чистая: возвращает новое состояние, не меняет входы, не вызывает БД и не коммитит.
  Вызывающий присваивает результат и сохраняет его один раз после исполнения.
- Кандидаты переводят состояние в `choice` (массовое `set_status` с `all = True` — в
  `confirm`), записывают `pending`, `candidates` и `shown` в исходном порядке, без группировки. Успешный выбор очищает ожидание
  и заменяет `shown` выбранными записями.
- Успешные создание, изменение и статус обновляют `last_action`. Список, поиск,
  справка, вопросы и ошибки его сохраняют. Откат очищает `last_action`;
  непустой `restored` тоже очищает прежнее действие, даже если новая цель неоднозначна.
- Фокус ставится на единственную созданную/изменённую/показанную запись,
  снимается при пустом или множественном результате. При откате используется `restored`.
- `agent/focus.py` оставлен только как совместимый импорт `focus_record_id`.
  Отдельного сохранения через `remember_focus` и подавления ошибок БД больше нет.

Обработчики изменения, статуса, отката, разрешение цели и несколько tool calls — в
разделе «Изменение записей (agent-07, agent-09)». `before` передаётся в общий переход;
агент не записывает эти поля в обход него.

## Контекст и порядок записей

`build_state_context(state, records, timezone_name)` в `agent/context.py` принимает
уже загруженные записи и возвращает не больше четырёх строк:

- `Показано:` — до 10 записей под номерами; название, тип, дата/время в поясе пользователя,
  «весь день», срок или «без даты». Выполненные и отменённые помечаются.
- `В фокусе:` — одна запись.
- `Последнее действие:` — действие и названия/даты затронутых записей.
- `Черновик:` — компактный JSON действия, `missing` и `awaiting`.
  Если частичного действия нет, передаётся только ожидание уточнения.

Пустое состояние даёт пустую строку. UUID, `before`, история сообщений и настройки LLM
в контекст не входят. Кавычки и переводы строк экранируются; данные не являются
инструкциями. Недоступные/чужие записи пропускаются. Номера не уплотняются:
если запись 1 удалена, запись 2 остаётся номером 2, соответствующим `shown[1]`.
Промпт связывает «вторую» с `target.index`, «её/эту» и поправку — с `target.focus`.

`agent/presentation.py::group_records` — общий источник групп для ответа и `shown`.
Одинаковые название, тип и статус группируются в порядке первого появления.
Представитель — последняя по дате запись (`start`, иначе `deadline`, иначе `created_at`).
Пример: «Созвон — 7 раз, последний 22.08.2026». Разные типы/статусы не склеиваются.
У поиска (`first_in_order=True`) представитель — первый в порядке выдачи, то есть ближайший:
будущий — «ближайший 30.10.2026», прошедший — «последний».
`shown_records` возвращает представителей первых 10 групп.
Шаблоны списка и поиска используют те же группы и номера; вслух — максимум три группы.
Полная исходная выдача остаётся в `ActionResult.records`. Кандидаты не группируются.

## Черновик и смена темы

Продолжение черновика создания — `create_record` того же типа или `ask_user`.
Первый самостоятельный запрос выполняется, оставляет черновик и выставляет
`pending_skipped=True`; ответ напоминает о нём. Второй подряд самостоятельный запрос
сбрасывает черновик. Создание другого типа сбрасывает его сразу.
Ответ по черновику снимает `pending_skipped`, затем идёт обычное слияние и проверка сервиса.

Поэтому «встреча завтра» → «что у меня завтра?» → «в 16» завершает встречу,
а после двух посторонних запросов «в 16» уже не имеет черновика для продолжения.
Ошибка LLM не меняет сохранённый черновик. Ошибка сервиса при продолжении сохраняет
уточнённые данные и ожидание. Ошибка сохранения состояния пробрасывается:
подтверждение успешного сохранения вместо неё не выдаётся.

## Даты и время

Дата без времени — локальные 00:00 и `time_given=false`; `start=null` — даты нет.
Для встречи без времени сервис возвращает `missing=["start"]`, даже если дата уже есть.
Время без даты пока относится к дате черновика, иначе — к сегодня.
Прошлое время не переносится на завтра.

Описания полей задают:

- Период списка — `[date_from, date_to)`. Для целых дней конец — 00:00 дня после
  последнего дня периода, не 23:59. «На неделю» — с текущего понедельника;
  «на следующей неделе» — со следующего; выходные — суббота–понедельник.
- «До конца недели» в списке — сегодня 00:00 до следующего понедельника 00:00.
  Без периода начало — сегодня 00:00, конец — `null`.
- «Сегодня вечером» в списке — 18:00 до завтра 00:00.
  `deadline` «до конца недели» остаётся воскресеньем 23:59:59.
- При создании «следующий <день недели>» — день следующей календарной недели;
  «на выходных» — суббота; «в конце месяца» — последний день.
- Общее правило промпта: день недели, совпадающий с сегодняшним, — через семь дней.
  Явное «сегодня» или конкретная дата имеют приоритет.

`SearchFilters` использует такие же границы целых дней, но неназванные границы
остаются `null`. Смещение вычисляется для даты в поясе пользователя.

## Хранение и интеграция

Миграция `0003_conversation_context` добавляет уже согласованные поля
`shown`, `last_action`, `pending_skipped` в ORM и PostgreSQL.
`services.conversation` сохраняет и загружает их вместе с остальным состоянием.
Перед запуском обновлённого агента: `uv run alembic upgrade head`.

Агент не вызывает commit. В текущей ветке сервисы ещё коммитят сами;
единая транзакция на реплику остаётся работой backend-03. При объединении его ветки
нужно согласовать миграцию этих трёх колонок, чтобы не добавить их повторно.
Атомарность создания записи и сохранения состояния здесь ещё не обеспечена.

`/api/chat` пока использует `handle_without_llm`; подключение агента остаётся agent-05.
Реестр `agent/actions.py` исполняет создание, список, поиск и справку.
`SearchRecords` пока вызывает поиск по подстроке: каждое слово длиннее двух букв,
фильтры по контракту, отменённые скрыты по умолчанию. Подмена на смысловой поиск —
в `handle_search_records`. Вызовы БД последовательные через `asyncio.to_thread`.

## Клиент LLM и ошибки

`make_client` берёт `base_url`, `api_key`, `model` из `LLMConfig`, затем из
`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. Пустой адрес означает OpenAI по умолчанию.
Таймаут 15 секунд, один повтор. Модель не вызывается повторно для текста ответа.

`LLMConfigError` даёт ответ о ненастроенном ассистенте, `openai.APIError` —
о временной недоступности, `ActionParseError` — просьбу переформулировать.
Состояние ожидания сохраняется; `ConversationAccessError` передаётся вызывающему API.

## Быстрые ответы — `awaiting` (agent-10)

Сервер прямо говорит, чего ждёт от следующей реплики (`api.md`, «Правила»): по `awaiting`
интерфейс рисует чипы. Нажатие чипа — обычная реплика, отдельного API нет.

| `awaiting` | Когда ставит `update_state` (`agent/state.py`) | Чип отправляет |
|---|---|---|
| `choice` | кандидаты для одной записи: несколько точных или только похожие | «номер N» |
| `confirm` | кандидаты массового `set_status` (`target.all = True`), 2–20 записей | «да, все» / «отмена» |
| `time` | вопрос о времени встречи, у которой день известен (условие ниже) | «в 09:00» и т. п. |
| `answer` | любой другой вопрос: нет названия, нет дня, уточнение не про встречу | — |

Пока ждём выбора или подтверждения, новый вопрос модели ожидание не меняет.

**«номер N» без модели** (`chosen_number`, `choose_candidate` в `agent/state.py`; перехват — в
`process_user_turn` сразу после отказа):
- при `choice` и `confirm`, если в `pending` — изменение или статус, реплика целиком «номер N»
  без учёта регистра, лишних пробелов и знаков препинания («Номер 2.» — тоже);
- N от 1 до числа кандидатов → действие из `pending` с `TargetRef(index=N)`, номер — N-я
  запись `candidates` (как в чипе), даже если экран с тех пор сменился. Дальше — обычный путь
  изменения: исполнение, `last_action`, ответ. При `confirm` «номер 2» меняет только вторую;
- N вне диапазона → «Нет записи под номером N.», ничего не меняется, ожидание остаётся;
  кандидаты снова в `result.candidates` — интерфейс показывает тот же список и чипы;
- без ожидания выбора «номер 2» — обычная реплика для модели.
Зачем без модели: нажатие чипа должно срабатывать всегда и сразу, без лишнего вызова и без
риска, что модель поймёт иначе.

**«да, все» и «отмена».** «Да, все» разбирает модель — `set_status` с `all = True` без описания
применяется ко всем кандидатам (`confirming` в `agent/changes.py` теперь смотрит на
`confirm`). «Отмена» — отказ без модели, как при любом ожидании: ничего не меняется.
«Нет» отказом не считается: «нет, в 16» — это ответ.

**Условие `time`** (`asks_meeting_time` в `agent/state.py`), по черновику в `pending`:
- `CreateRecord` встречи с днём без времени (`start` есть, `time_given = False`), сервис
  ответил `missing = ["start"]` («Не названо время встречи»);
- или вопрос модели с черновиком `AskUser.draft`: тип — встреча, `start` (день) есть,
  времени нет (`time_given` не `true`, отдельного `time` нет), в `missing` — `start` или `time`.

Встреча без дня («в 14:45, а когда?») и без времени вообще («поставь встречу с Дмитрием») —
`answer`: спрашиваем день. Ответ «в 15:00» дополняет черновик как любой ответ на уточнение.

## Изменение записей (agent-07, agent-09)

Модель получает инструменты `update_record`, `set_status`, `undo_last` (правило 6
промпта: когда что вызывать). Они идут мимо `execute`: им нужны цель из состояния
разговора и прежние значения для отката. `process_user_turn` вызывает
`execute_change(db, user_id, action, state, now=now)` из `agent/changes.py`, получает
`ChangeOutcome` (`result`, `before`, признаки `similar` и `confirm`), передаёт `before` в
`update_state` и строит ответ в `agent/change_replies.py`.

### Цель изменения

`agent/targets.py`, `resolve_target(...)` → `Target` (записи, кандидаты или ошибка):

- `index` — `shown[index - 1]`; номера нет — «В показанном списке нет записи № N»;
- `focus` — `focus_record_id`; фокуса нет — «Какую запись? …»;
- `all` без описания — все записи из `shown` (ответ «да», «все» на подтверждение);
- `text`, `when`, `filters` — `find_target()` модуля поиска (`search.md`) с `limit=21`.
  Среди каких записей искать: `[active]`, для «верни в активные» и «не выполнено» —
  `[done, cancelled]`. Агент сам записи не ищет и кандидатов не сортирует.

Исход `find_target()`:

| Исход | Что делает агент |
|---|---|
| одна точная | исполняет |
| несколько точных | ничего не меняет; `candidates`, `shown`, `pending`, `awaiting="choice"`; «Подходит несколько: 1) … 2) …. Какую?» |
| только похожие | ничего не меняет; то же ожидание выбора; «Точно такой нет. Может, «…»?» (одна) или «…Может, одна из этих: 1) …?» |
| ничего | `ok=False`, «Не нашёл «…»» |

Похожая запись без ответа пользователя не меняется никогда. Ответ «да», «вторую»,
нажатие чипа приходят текстом; модель видит «Показано» и возвращает то же действие с
`index` — оно исполняется, черновик и кандидаты очищаются.

Несколько записей одной командой (`set_status`, `target.all=true` с описанием) — только
точные: больше 20 — «Слишком много записей. Уточните, какие»; одна — сразу; несколько —
подтверждение «Отменить 3 записи: 1) …?» с `awaiting="confirm"`, после «да» — все из
`shown` одним ходом.
`update_record` для нескольких записей сразу — вне задачи, ответ просит назвать одну.

Пока нет search-01, `find_target()` — заглушка в `services/search_stub.py`: «точно» —
основы всех значимых слов описания есть в названии (слова типа записи — «встреча»,
«задача», «напоминание» — пропускаются), сужение по `when` как в контракте; похожих по
смыслу заглушка не находит — точные по словам, не подошедшие под время, уходят в
`similar`. Замена — одна строка импорта в `agent/targets.py` (`TODO`).

### Действия и откат

- `update_record` меняет только переданные поля (сервис `update_record`); пересечения —
  в ответе: «В это же время: …».
- `set_status` — сразу, без подтверждения: отмена обратима. Ответ на отмену называет
  запись и дату и предлагает «верни».
- `undo_last` откатывает `last_action`: изменение — `restore_record` с `before`, смену
  статуса — прежним статусом, создание — отменой созданной записи. Откаченные — в
  `restored`. Второе «верни» — «Нечего возвращать.»
- `replaces_last=true` («нет, не этот, а тот, что по сайту»): сначала откат, потом то же
  действие с новой целью; ответ одной фразой: «Вернул «…». Отменил: «…».». Новая цель
  неоднозначна — откат уже сделан, дальше обычный выбор.
- Поправка сразу после создания («нет, не в 15, а в 16») — `update_record` с `focus`:
  фокус стоит на созданной записи.

Поправки по живому прогону 27.10.2026 — модель ошибается одинаково, код это выравнивает:

- «Перенеси на пятницу»: модель присылает полночь без `time_given`. Код ставит прежнее время
  записи (и сдвигает конец встречи на ту же величину) — `keep_time` в `agent/changes.py`.
- «Нет, не этот, а тот»: модель путает статус с «верни» (`active`). При `replaces_last`
  статус берётся у записи из прошлого действия.
- «Перенеси встречу с Натальей на час позже»: записи нет в контексте, модель не знает её
  время и не может посчитать новое. Поэтому у `update_record` есть `shift_minutes` — сдвиг
  от текущего времени записи («на час позже» = 60, «на полчаса раньше» = -30, «на день
  позже» = 1440). Модель передаёт только сдвиг, время считает код (`apply_shift` в
  `agent/changes.py`): у записи со временем сдвигается начало (конец встречи — сервис, на ту
  же величину), у задачи только со сроком — срок. Вызов модели остаётся один на реплику
  (решение техлида вместо повторного запроса с записью в фокусе). Изменение без полей и без
  сдвига — вопрос «Что изменить у этой записи?».
- «Да» на «Отменить 3 записи?»: модель повторяет описание (`all` с фильтрами). Подтверждение —
  это то же массовое действие с тем же статусом, что ждёт в `pending`: без описания оно берёт
  кандидатов, с описанием — если `find_target()` нашёл ровно их. Иначе это новый запрос
  («отметь отчёт…» → выбор → «отмени все созвоны»): своё подтверждение, старые кандидаты не
  трогаются.
- `target.focus` без фокуса, но с описанием — поиск по описанию, а не «Какую запись?».

Массовое действие — всё или ничего (иначе маршрут закоммитил бы часть изменений без
`last_action`, и «верни» их бы не откатил). Оно идёт в общей точке сохранения
(`begin_nested`): сервис отказал на одной из записей — точка откатывается целиком. Без точки
сохранения (сессия-заглушка в тестах) уже изменённые записи возвращаются сервисами; если и
это не удалось — `MassChangeError`, и маршрут `/api/chat` откатывает транзакцию реплики.
Ответ и `update_state` получают исправленное действие (`ChangeOutcome.applied`: статус
прошлого действия, время записи после сдвига), в том числе в черновик при выборе.

### Поиск: «похожие»

`search()` помечает результаты `match`. Если все `similar`, обработчик поиска возвращает
`SearchResult` (подкласс `ActionResult` с полем `similar`), и ответ — «Точно не нашёл
«договор аренды». Похожие: …». Поле нужно только шаблону: `ChatResponse.result` объявлен
как `ActionResult`, наружу `similar` не уходит, контракт API прежний.

### Несколько команд в одной фразе

Проверка живым запросом 27.10.2026, модель по умолчанию `gemini-3.5-flash-lite` через
OpenAI-совместимый адрес. Три фразы с двумя командами («запиши задачу подготовить акт и
ещё поставь встречу с Максимом завтра в 16», то же без «ещё», «напомни завтра в 10
позвонить маме и в 12 позвонить папе»), по три варианта параметров: `tool_choice="required"`
(как в продукте), он же с `parallel_tool_calls=true`, `tool_choice="auto"` с
`parallel_tool_calls=true`. **Во всех 9 ответах — один вызов**: модель выбирает одну из
команд (обычно первую, один раз — вторую), вторую молча отбрасывает.

Поэтому поведение — «первая команда + остальное скажите отдельно»:

- модель всё же вернула несколько вызовов — исполняется первый (раньше это была ошибка
  разбора), ответ заканчивается «Остальное скажите отдельно.»;
- вызов один, но во фразе не меньше двух глаголов-команд («запиши … поставь …»,
  `several_commands` в `agent/agent.py`) — то же окончание ответа. Фраза «позвонить маме и
  в 12 позвонить папе» с одним глаголом так не распознаётся: вторая команда теряется молча.

Кейс 8.9 допускает этот исход.

## Подключение к `/api/chat` (agent-05)

Маршрут `api/chat.py` проверяет пояс (`parse_timezone`), владельца разговора (чужой или
несуществующий `conversation_id` — 404) и
вызывает `process_user_turn(db, user.id, conversation_id, req.text, zone.key, req.llm_config)`.
В агента идёт уже проверенный пояс `zone.key`.

- **Сессия БД** приходит в маршрут через `Depends(get_session)` и передаётся агенту аргументом
  `db`. Агент сессию не открывает и не закрывает.
- **Обёртка в поток** — в местах вызова: обработчики `agent/actions.py` и загрузка/сохранение
  состояния в `agent/agent.py` вызывают синхронные сервисы через `asyncio.to_thread`,
  последовательно, без одновременного использования одной сессии.
- **Транзакции.** Агент не коммитит. Пока сервисы `create_record` и
  `save_conversation_state` коммитят сами — это две транзакции на реплику (последствия описаны
  в ограничениях выше). После backend-03 сервисы перестают коммитить, коммит один — в маршруте.
- **Ответ** на создание подтверждает дату и время во времени пользователя; задача на весь день
  называется без «00:00». Ошибки бизнес-правил («дата в прошлом») приходят текстом, без 500.

## Автотест (agent-08)

Эталонные кейсы из `docs/test-cases.md` — данными в `backend/tests/agent_cases.py`:
номер ровно как в таблице, реплики и ожидание по полям (действие, тип, дата и время,
`time_given`, срок, период и типы списка, ключевые слова названия или запроса, результат
исполнения, ожидание ответа). Сверяется подмножество: лишние поля ответа модели тест не
роняют. Даты сравниваются как моменты в поясе пользователя с точностью до минуты,
название — по основам слов. Текст ответа (`reply`) не сверяется: это шаблоны в коде, у них
свои тесты.

«Сейчас» — среда 21.10.2026 10:00; пояс в таблице не назван, автотест берёт
`Europe/Moscow`. Время подставляется через `process_user_turn(..., now=...)`.

Два слоя:

- **Быстрый** — в CI, без модели и ключа. `test_agent_cases_sync.py` сверяет номера с
  таблицей в обе стороны (раздел 9 — по строке «Выражение»), `test_agent_compare.py`
  проверяет сравниватель, `test_agent_harness.py` — прогонщик со сценарием вместо модели.
  `test_agent_harness_db.py` прогоняет кейсы на тестовой PostgreSQL с настоящими сервисами
  записей и состоянием разговора: сохранённый черновик после первого шага, созданная запись
  после второго, отсутствие записи при ошибке. Модель-сценарий во второй реплике возвращает
  чужое название — верное приходит только из сохранённого черновика. Там же «идеальная
  модель»: для каждого кейса с базой (раздел 7, 1.16, 8.5, 8.7, 8.8) задан правильный ответ
  модели, и кейс проходит на настоящем коде — падение значит, что ожидание в
  `agent_cases.py` и код агента разошлись.
- **Живой** — `test_agent_live.py`, маркер `live`. Реплики идут через настоящий
  `process_user_turn` и настоящую модель; состояние разговора хранится в памяти, создание
  проверяется настоящими бизнес-правилами `validate_create`, в базу ничего не пишется —
  база для прогона не нужна. У создания по умолчанию ожидается успех и завершённое уточнение (`ok=True`, нет
  ожидания ответа); отрицательные сценарии задают исключение явно. У `start` со временем
  требуется `time_given=true`, у даты без времени — `false`.

  Изменения записей (раздел 7) и пересечения (8.5, 8.7, 8.8) проверяются только на базе.
  У таких кейсов `records` — записи пользователя до первой реплики (вместо стартового
  набора и колонки «Предусловие»), и прогон создаёт их перед кейсом. С
  `TEST_DATABASE_URL` живой прогон идёт на тестовой базе с настоящими сервисами, всё в одной
  транзакции с откатом; без неё эти кейсы пропускаются с причиной. Локально база —
  `docker compose up -d postgres`, адрес — через `127.0.0.1`, не `localhost` (на Windows
  `localhost` сначала пробует IPv6, а порт открыт только на IPv4). Включается только явно:

  ```powershell
  $env:AGENT_LIVE="1"; uv run pytest -m live -s                          # весь набор
  $env:AGENT_LIVE="1"; $env:AGENT_SECTION="2,3"; uv run pytest -m live -s # разделы
  $env:TEST_DATABASE_URL="postgresql://postgres:postgres_password@127.0.0.1:5432/hackathon_db"
  $env:AGENT_LIVE="1"; $env:AGENT_SECTION="7,8"; uv run pytest -m live -s # раздел 7 — с базой
  Remove-Item Env:AGENT_LIVE, Env:AGENT_SECTION                          # выключить
  ```

  `AGENT_PAUSE` — пауза перед вызовом модели в секундах (по умолчанию 4),
  `AGENT_MIN_RATE` — минимальная доля прошедших в процентах (по умолчанию 0, порог
  назначит техлид). Прогон печатает строку после каждого кейса, в конце — долю прошедших и
  по каждому упавшему номер, фразу, ожидание, полученное действие и расхождения. Если
  модель не ответила три кейса подряд, прогон прерывается: провайдер недоступен.
  Полный набор — около 150 вызовов модели, поэтому удобнее запускать по разделам.

**Когда обязателен живой прогон:** PR трогает системный промпт (`agent/system_prompt.py`),
инструменты (`agent/tools.py`), схемы действий (`backend/schemas/actions.py`) или
`process_user_turn`. Результат — в описание PR.

**Как добавить кейс:** строка в таблице `test-cases.md` и кейс с тем же номером в
`agent_cases.py` (`one(...)` для одной реплики, `dialog(...)` для нескольких). Сверка
номеров упадёт, если забыть одно из двух. Кейс, для которого ещё нет действия или
состояния разговора, получает `skip="причина"` — его не удаляют и не переписывают под
текущее поведение.
