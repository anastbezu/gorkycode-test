# Контракт: API чата

Граница: фронтенд (Ася) ↔ бэкенд (Денис). Pydantic v2, документация OpenAPI — `/docs`. `ActionResult` — `agent-tools.md`.

```python
from typing import Literal
from uuid import UUID
from pydantic import BaseModel, Field

class LLMConfig(BaseModel):
    base_url: str | None = Field(default=None, description="OpenAI-совместимый base_url")
    api_key: str | None = Field(default=None, description="Ключ API пользователя")
    model: str | None = Field(default=None, description="Имя модели у провайдера")

class ChatRequest(BaseModel):
    conversation_id: UUID | None = None  # None — новый разговор
    text: str
    timezone: str = Field(description="IANA-пояс браузера, напр. Europe/Moscow")
    llm_config: LLMConfig | None = Field(default=None, description="Пользовательские настройки LLM (если заданы в браузере)")

class ChatResponse(BaseModel):
    conversation_id: UUID
    reply: str                          # текст ответа: показывается в чате и озвучивается как есть
    result: ActionResult | None = None  # что сделано — для показа в интерфейсе
    awaiting: Literal["answer", "choice", "confirm", "time"] | None = None  # чего ждёт ассистент — правило ниже
```

## Правила
- Клиент шлёт только новую реплику, `conversation_id` и часовой пояс; историю и состояние разговора хранит сервер.
- `reply` — один текст и для чата, и для голоса: интерфейс показывает его и озвучивает без изменений, отдельного текста для озвучки нет. Поэтому `reply` короткий и удобный на слух; подробности — в `result`.
- Нумерованный список в интерфейсе: `result.candidates`, если они не пустые, иначе `result.records` ответа на список или поиск (`list_records`, `search_records`). Номера с 1 в полученном порядке, у каждой записи своя строка и свой номер: без группировки одинаковых и без пересортировки; заголовки дней между строками допустимы, номера идут подряд. Этот номер пользователь называет в следующей реплике («перенеси вторую») — он совпадает с `shown` (`data-model.md`).
- `awaiting` — чего ассистент ждёт от следующей реплики; интерфейс по нему рисует быстрые ответы. Нажатие быстрого ответа отправляет обычную реплику — то же можно сказать голосом:
  - `null` — ничего не ждёт;
  - `"answer"` — ответа на вопрос в `reply` (кроме времени встречи); быстрых ответов нет;
  - `"choice"` — выбора одной записи из `result.candidates`; быстрый ответ — запись под номером N, отправляет «номер N»;
  - `"confirm"` — подтверждения действия над всеми записями из `result.candidates` (массовая отмена или выполнение, `agent-tools.md`, «Цель изменения»); быстрые ответы — «Да, все» (отправляет «да, все») и «Отмена» (отправляет «отмена» — отказ, как у любого ожидания, ничего не меняет);
  - `"time"` — времени встречи, у которой уже известен день; быстрые ответы — 09:00, 13:00, 15:00, 18:00 (умолчания «утром», «в обед», «днём», «вечером», `agent-tools.md`, «Правила»), отправляют «в 09:00» и т. п.
- Пользовательские настройки LLM (`llm_config`): если переданы, сервер использует их для обращения к модели; если нет — используются настройки по умолчанию из `.env` сервера (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`). Сервер ключ не сохраняет.
- Пользователь — учётка или гость, не в теле запроса (раздел «Учётки и вход»). Правило общее для всех эндпоинтов `/api/*`, кроме входа и регистрации:
  - учётка — заголовок `Authorization: Bearer <token>`; токен недействителен (неверный, истёк, после выхода) — 401, интерфейс забывает токен и продолжает гостем; с токеном `X-User-Id` не читается и не выдаётся;
  - гость — заголовок `X-User-Id` (UUID). Без заголовка сервер выдаёт новый UUID в заголовке ответа `X-User-Id`; значение не UUID — 400.
  - Гость и новая учётка начинают без записей.
- `GET /api/items` — `list[Record]` для боковой панели «Мои дела»:
  - `from`, `to` — обязательные, ISO 8601 со смещением, период `[from, to)`;
  - `type` — фильтр по типу, можно несколько;
  - `tz` — IANA-пояс, даты в ответе — в этом поясе;
  - `include_undated` (по умолчанию `false`) — добавить в конец активные записи без даты (`start` и `deadline` пустые) для блока «Без срока».
- `POST /api/chat`: чужой или несуществующий `conversation_id` → 404, неизвестный `timezone` → 422.

## Распознавание речи

Граница: фронтенд (Ася) ↔ бэкенд (Денис). Голос идёт в два шага: запись → `POST /api/stt` → текст → обычный `POST /api/chat` с этим текстом. Контракт чата для голоса не меняется.

```python
class STTResponse(BaseModel):
    text: str  # распознанная реплика как есть: не пустая, без правок и сокращений
```

### Правила
- `POST /api/stt`, тело `multipart/form-data`, одно поле `audio` — файл записи в том формате, который отдал `MediaRecorder` браузера: `audio/webm` (Chrome, Android), `audio/mp4` (Safari, iOS), `audio/ogg`, `audio/wav`. Формат — из `Content-Type` файла. Сервер не перекодирует запись и не сохраняет её на диск.
- Пользователь — как у `/api/chat`: токен учётки или `X-User-Id` гостя.
- Язык — русский. Сервис распознавания и ключ — из `.env` сервера; `llm_config` пользователя распознавание не использует.
- Запись не длиннее 30 секунд: интерфейс останавливает запись сам, сервер отклоняет длиннее.
- Ответ `200` — `STTResponse`. Интерфейс показывает `text` в ленте как реплику пользователя и сразу отправляет его в `POST /api/chat`.
- Ошибки — статус и `{"detail": "<текст для пользователя>"}`; интерфейс показывает `detail` и ничего не отправляет в чат:

| Код | Когда |
|---|---|
| 400 | `X-User-Id` не UUID |
| 401 | токен учётки недействителен |
| 413 | запись длиннее 30 секунд |
| 415 | формат файла не из списка выше, или поле `audio` пустое |
| 422 | речь не распознана: тишина, шум, пустой результат |
| 429 | слишком много запросов от одного пользователя или от всех вместе (защита серверного ключа) |
| 503 | сервис распознавания недоступен: сеть, таймаут, лимит провайдера, не задан ключ |

- Озвучка ответа — в браузере (`speechSynthesis`): интерфейс озвучивает `reply` как есть. Серверного синтеза нет.

## Учётки и вход

Граница: фронтенд (Ася) ↔ бэкенд (Денис). Вход по желанию: без него страница работает гостем.

```python
class Credentials(BaseModel):
    login: str = Field(min_length=3, max_length=32, pattern=r"^[A-Za-z0-9_.-]+$")
    password: str = Field(min_length=8, max_length=128)

class Account(BaseModel):
    id: UUID      # тот же user_id, что у записей и разговоров учётки
    login: str
    demo: bool    # демо-учётка с датасетом

class AuthResponse(BaseModel):
    token: str    # клиент присылает его в `Authorization: Bearer <token>`
    account: Account
```

### Правила
- `POST /api/auth/register`, тело `Credentials` → `201 AuthResponse`: учётка создана и вход выполнен. Логин занят — 409.
- `POST /api/auth/login`, тело `Credentials` → `200 AuthResponse`. Неверный логин или пароль — 401, одним текстом: не подсказывает, что из двух неверно.
- `POST /api/auth/logout` с токеном → 204; после выхода этот токен не принимается.
- `GET /api/auth/me` с токеном → `Account`; это способ проверить сохранённый токен при открытии страницы.
- Логин сравнивается без учёта регистра. Вид токена, срок его жизни и хранение паролей — устройство бэкенда; пароль нигде не хранится и не пишется в лог открытым текстом.
- Новая учётка — без записей. Записи и разговоры гостя к учётке не переходят: после входа или выхода прежний `conversation_id` — 404, интерфейс начинает новый разговор.
- Демо-учётки (для жюри и для команды) — список логинов и паролей в `.env`, одинаково на сервере и при локальном запуске. Одна серверная команда создаёт недостающие с копией датасета и сбрасывает указанную к ней; через API их не создают и не сбрасывают. Пароль учётки жюри дополнительно — в README.
- Срок хранения: гость без запросов 30 дней удаляется вместе с записями и разговорами; запись, отменённая больше 30 дней назад, удаляется насовсем — «Вернуть» по ней даёт 404. Учётки и демо-учётки чистка гостей не трогает.
- Ошибки — статус и `{"detail": "<текст для пользователя>"}`: 401, 409, 422 (логин или пароль не по правилам `Credentials`), 429 (слишком много попыток входа).

## Записи из интерфейса

Граница: фронтенд (Ася) ↔ бэкенд (Давид). Кнопки в карточке и календаре делают то же, что агент, теми же сервисами и с теми же проверками, но без LLM.

```python
class CreateItem(BaseModel):
    type: RecordType
    title: str = Field(min_length=1)
    start: AwareDatetime | None = None
    end: AwareDatetime | None = None       # только у встречи
    time_given: bool = True                # false — «весь день»: start — начало дня
    deadline: AwareDatetime | None = None

class UpdateItem(BaseModel):               # передаются только меняемые поля
    title: str | None = None
    start: AwareDatetime | None = None
    end: AwareDatetime | None = None
    time_given: bool | None = None
    deadline: AwareDatetime | None = None

class SetItemStatus(BaseModel):
    status: RecordStatus  # done — «выполнено»; cancelled — «удалить»; active — «вернуть»
```

### Правила
- `POST /api/items`, тело `CreateItem` → `201 ActionResult`; `PATCH /api/items/{id}`, тело `UpdateItem` → `200 ActionResult`; `POST /api/items/{id}/status`, тело `SetItemStatus` → `200 ActionResult`. В `records` — одна запись, у встречи в `conflicts` — пересечения.
- Пользователь — как у `/api/chat`. Параметр `tz` — IANA-пояс, даты в ответе в нём, как у `GET /api/items`.
- Проверки — как у действий агента `create_record`, `update_record`, `set_status` (`agent-tools.md`) и правил `data-model.md`: у встречи есть начало, конец позже начала, новая дата не в прошлом. Перенос начала встречи без нового конца сохраняет длительность. Пересечение не мешает сохранению — запись сохраняется, интерфейс предупреждает.
- `None` в `UpdateItem` — «не менять»: убрать дату или срок этим эндпоинтом нельзя, как и у `update_record`.
- Удаление — мягкое: `status = cancelled`, запись пропадает из `GET /api/items`; «Вернуть» — `status = active` по тому же `id`. Насовсем запись удаляет только чистка по сроку хранения (раздел «Учётки и вход»).
- Изменение из интерфейса не пишется в состояние разговора, но сбрасывает `last_action` разговоров пользователя, если оно затрагивает эту запись: «верни» в чате не откатит старое изменение поверх ручного. Номера на экране (`shown`) и фокус не меняются.
- Один запрос — одна транзакция: при ошибке ничего не сохраняется.
- Ошибки — статус и `{"detail": "<текст для пользователя>"}`:

| Код | Когда |
|---|---|
| 400 | `X-User-Id` не UUID |
| 401 | токен учётки недействителен |
| 404 | записи нет или она чужая |
| 422 | тело не по схеме или проверка не прошла: дата в прошлом, конец раньше начала, встреча без начала, нечего менять — `detail` из `ActionResult.error` |

## Внешний календарь (Google)

Граница: фронтенд (Ася) ↔ бэкенд (Илья, calendar-01). Подключение — у учётки: гость его не видит, у гостя нет постоянной личности, к которой привязать Google. Агент и действия LLM не меняются: в Google ходит бэкенд после успешной операции своих сервисов, правда — в нашей базе.

```python
class GoogleCalendarStatus(BaseModel):
    state: Literal["not_connected", "connected", "error"]
    email: str | None = None   # аккаунт Google, если подключён
    error: str | None = None   # текст для пользователя: «Доступ к Google Календарю отозван — переподключите»
    pending: int = 0           # сколько записей ждут отправки в Google
```

### Правила
- Только учётка (`Authorization: Bearer`); гость — 403, интерфейс гостю блок подключения не показывает.
- `GET /api/calendar/google` → `GoogleCalendarStatus`.
- `POST /api/calendar/google/connect` → `{"auth_url": "<адрес страницы Google>"}`; интерфейс переходит по нему. Повторный вызов при подключённом — переподключение (новое согласие).
- `GET /api/calendar/google/callback?code=…&state=…` — сюда Google возвращает пользователя; бэкенд сохраняет подключение и перенаправляет на `/?calendar=connected` или `/?calendar=error`. `state` связывает возврат с учёткой. Интерфейс этот адрес не вызывает.
- `DELETE /api/calendar/google` → 204: доступ отзывается в Google и удаляется у нас; события, уже созданные в Google, остаются; синхронизация прекращается.
- Записи уходят в отдельный календарь «Голосовой ассистент», который бэкенд создаёт в Google пользователя при подключении (разрешение `calendar.app.created`: другие календари пользователя приложение не видит).
- Направление — только наши записи → Google: создание, перенос, переименование, отмена («удалить» → событие удаляется), «верни» (событие восстанавливается), выполнено (к названию — «✓»). Записи без даты в Google не уходят. Правки, сделанные в Google, к нам не возвращаются и перезаписываются при следующем изменении записи у нас; события из Google у нас не показываются.
- При подключении в Google один раз уходят записи учётки с датой в ближайшие 2 недели (от сегодня). Остальные — только когда их создают или меняют у нас; датасет демо-учётки целиком не выгружается.
- Сбой Google не меняет ответы `/api/chat` и `/api/items` по сути: запись у нас сохранена всегда. Не ушло в Google — в конце `reply` фраза «В Google Календарь пока не ушло, повторю позже», запись догоняет при следующем запросе пользователя; доступ отозван — `state = "error"`.
- `ChatResponse`, `Record` и `ActionResult` не меняются.
- Ошибки — статус и `{"detail": "<текст для пользователя>"}`:

| Код | Когда |
|---|---|
| 401 | токен учётки недействителен |
| 403 | гость (нет учётки) |
| 503 | подключение Google не настроено на сервере (нет ключей в `.env`) |
