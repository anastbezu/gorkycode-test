# Архитектура

> Черновик. Конкретные технологии будут указаны после выбора стека (см. [decisions.md](decisions.md)).

## Поток запроса

```
Браузер ── аудио / текст ──► Голос (STT) ──► текст
                                              │
                                              ▼
                                   Агент: понимание запроса
                          (LLM + tools, разбор дат, состояние диалога)
                                              │ вызов tool
                                              ▼
                                   Сервисы (бизнес-логика)
                               создать / список / найти / изменить
                                     │                 │
                                     ▼                 ▼
                                Хранилище          Поиск по смыслу
                                     │
                          текст ответа ◄────────────┘
                                              │
Браузер ◄── аудио / текст ── Голос (TTS) ◄────┘
```

## Модули

| Модуль | Отвечает за | Владелец |
|---|---|---|
| Голос | запись в браузере, распознавание и синтез речи | Ася (браузер), Денис (бэкенд) |
| Агент | намерения, параметры, даты, уточнения, ответ | Илья (создание), Давид (чтение и поиск) |
| Сервисы | создание, список за период, изменение записей | Денис |
| Хранилище | схема данных, миграции, импорт датасета | Денис |
| Поиск | семантический / гибридный поиск по записям | Родион |
| API | эндпоинты для фронтенда | Денис |
| Фронтенд | страница чата, состояния, воспроизведение | Ася |
| DevOps | репозиторий, CI, деплой | Ася |

Границы между модулями описаны в [contracts/](contracts/).

## Как обрабатывается реплика

На каждую реплику — один вызов LLM. Историю сообщений модель не получает: всё, что нужно помнить между репликами, хранит сервер в состоянии разговора ([`contracts/data-model.md`](contracts/data-model.md)), а модель видит его короткой выжимкой. Что можно сделать без модели — делает код.

Пример: пользователь спросил «Что у меня завтра?», ассистент назвал три дела, пользователь говорит «Перенеси вторую на пятницу».

1. **Состояние.** Сервер загружает состояние разговора. После прошлой реплики в нём сохранён показанный список — id трёх записей в том порядке, в каком ассистент их назвал.
2. **Проверка без модели.** Если ассистент ждёт ответа на вопрос, а пользователь сказал только «не надо» или «забудь», код сбрасывает черновик и отвечает сам — модель не вызывается. Здесь не тот случай, идём дальше.
3. **Промпт.** В системный промпт, кроме правил и календаря на две недели, код добавляет несколько строк о состоянии — без id:
   ```
   Показано: 1) Демо по сайту 22.10 10:00  2) Встреча с Иваном 22.10 15:00  3) Отчёт, весь день
   Последнее действие: —
   ```
4. **Вызов модели.** Модель обязана выбрать один инструмент ([`contracts/agent-tools.md`](contracts/agent-tools.md)) и возвращает «изменить запись № 2, новое начало — пятница 15:00». Номер она взяла из строки «Показано», время — из той же строки.
5. **Цель.** Код переводит номер 2 в id второй записи показанного списка. Если бы пользователь сказал «перенеси встречу с Иваном», а таких встреч несколько, код ничего бы не менял и вернул варианты для выбора.
6. **Проверки и исполнение.** Код проверяет, что новое время не в прошлом и не пересекается с другой встречей, и вызывает сервис изменения записи. Прежние значения полей сохраняются — по ним «верни» откатит перенос.
7. **Новое состояние.** Перенесённая запись становится фокусом («её»), перенос — последним действием. Теперь «нет, не в 15, а в 16» изменит именно её.
8. **Ответ.** Текст собирается по шаблону из результата: «Перенёс встречу с Иваном на пятницу, 23 октября, 15:00». Вместе с текстом интерфейс получает затронутые записи и обновляет «Мои дела».
