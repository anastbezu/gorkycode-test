# Архитектура

Как устроен прототип и как модули связаны между собой. Почему выбраны именно эти технологии — [decisions.md](decisions.md); устройство каждого модуля — [modules/](modules/); договорённости между модулями — [contracts/](contracts/).

## Поток запроса

```
Браузер ── аудио ──► Распознавание речи (POST /api/stt, Gemini) ── текст ──► Браузер
   │
   │ текст реплики (POST /api/chat)
   ▼
API (FastAPI) ── кто пользователь: токен учётки или id гостя
   │
   ▼
Агент ── состояние разговора ──► LLM (один вызов, tool calling) ──► действие и аргументы
   │
   ├──► Сервисы записей: создать / список / изменить / статус / откат
   │         │
   ├──► Поиск: «точно» по словам, «похожие» по векторам
   │         │
   │         ▼
   │    PostgreSQL + pgvector (записи, состояние, учётки, векторы)
   │
   ▼ один коммит на запрос
   ├──► после коммита: Google Календарь (если учётка подключила)
   ▼
Браузер ◄── текст ответа + затронутые записи; озвучка — голосом браузера (speechSynthesis)
```

Кнопки интерфейса («Мои дела», окно записи) идут мимо агента и LLM: `/api/items` вызывает те же сервисы записей.

## Как обрабатывается реплика

На каждую реплику — один вызов LLM. Историю сообщений модель не получает: всё, что нужно помнить между репликами, хранит сервер в состоянии разговора ([`contracts/data-model.md`](contracts/data-model.md)), а модель видит его короткой выжимкой. Что можно сделать без модели — делает код.

Пример: пользователь спросил «Что у меня завтра?», ассистент назвал три дела, пользователь говорит «Перенеси вторую на пятницу».

1. **Состояние.** Сервер загружает состояние разговора. После прошлой реплики в нём сохранён показанный список — id трёх записей в том порядке, в каком ассистент их назвал.
2. **Проверка без модели.** Если ассистент ждёт ответа на вопрос, а пользователь сказал только «не надо» или «забудь», код сбрасывает черновик и отвечает сам — модель не вызывается. Так же без модели код понимает «номер 2», когда ассистент ждёт выбора (так отвечает чип на экране). Здесь не тот случай, идём дальше.
3. **Промпт.** В системный промпт, кроме правил и календаря на две недели, код добавляет несколько строк о состоянии — без id:
   ```
   Показано: 1) Демо по сайту 22.10 10:00  2) Встреча с Иваном 22.10 15:00  3) Отчёт, весь день
   Последнее действие: —
   ```
4. **Вызов модели.** Модель обязана выбрать один инструмент ([`contracts/agent-tools.md`](contracts/agent-tools.md)) и возвращает «изменить запись № 2, новое начало — пятница 15:00». Номер она взяла из строки «Показано», время — из той же строки.
5. **Цель.** Код переводит номер 2 в id второй записи показанного списка. Если бы пользователь сказал «перенеси встречу с Иваном», а таких встреч несколько, код ничего бы не менял и вернул варианты для выбора.
6. **Проверки и исполнение.** Код проверяет, что новое время не в прошлом, ищет пересечения с другими встречами (они не мешают сохранить — ответ предупредит) и вызывает сервис изменения записи. Прежние значения полей сохраняются — по ним «верни» откатит перенос.
7. **Новое состояние.** Перенесённая запись становится фокусом («её»), перенос — последним действием. Теперь «нет, не в 15, а в 16» изменит именно её.
8. **Ответ.** Текст собирается шаблоном в коде из результата — название и новое время записи; формулировки — [assistant-texts.md](assistant-texts.md). Вместе с текстом интерфейс получает затронутые записи и обновляет «Мои дела». Модель текст ответа не пишет.
9. **После коммита.** Если учётка подключила Google Календарь, перенесённое событие обновляется и там.
