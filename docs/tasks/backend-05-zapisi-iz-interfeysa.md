# backend-05: записи из интерфейса — создать, перенести, выполнить, удалить и вернуть кнопкой

**Исполнитель:** Давид

## Зависимости

- **Пересечение с [backend-04](archive/backend-04-uchetki-i-vhod.md) (Денис).** Он меняет, как определяется пользователь (`backend/api/deps.py`: токен учётки или `X-User-Id` гостя). Ты берёшь пользователя той же зависимостью, что `/api/items` сейчас, и не меняешь её. Влит раньше его PR — подтяни `develop`, твои маршруты должны заработать с учётками без правок.
- **Сервисы записей — модуль Дениса.** Если для маршрутов нужно поменять сигнатуру сервиса — согласуй с ним.
- **Тебя ждёт:** [frontend-05](archive/frontend-05-deystviya-s-zapisyami.md) (Ася) — кнопки на странице.
- **Потом:** [voice-02](voice-02-neyrosetevaya-ozvuchka.md) — твоя следующая задача.

## Цель
Пользователь нажимает в карточке «Перенести» и выбирает пятницу 15:00 — запись переносится сразу, без вызова LLM, с той же проверкой пересечений, что в чате. Так же — «Выполнено», «Удалить» с «Вернуть» и «Создать».

## Контекст

### Это не новая логика агента
Агент уже умеет всё это голосом: создание, перенос, выполнено, отмена и возврат — сервисы `create_record`, `update_record`, `set_status` в `backend/services/records.py` (backend-03) и действия агента (agent-07). Но фронтенд может попасть к ним только через чат, а кнопка, которая шлёт фразу «перенеси запись 3 на пятницу», — это вызов LLM на каждый клик и риск, что модель поймёт не так, хотя действие известно точно. Поэтому решение техлида: **три REST-эндпоинта поверх тех же сервисов**, без LLM ([`decisions.md`](../decisions.md), «Управление записями из интерфейса»).

### Контракт — коротко
- `POST /api/items` (`CreateItem`) → 201, `PATCH /api/items/{id}` (`UpdateItem`) → 200, `POST /api/items/{id}/status` (`SetItemStatus`) → 200. Ответ — `ActionResult`, как у чата: в `records` одна запись, у встречи в `conflicts` — пересечения. Фронтенд уже умеет показывать карточку из `ActionResult`.
- Параметр `tz` — даты в ответе в поясе пользователя, как у `GET /api/items` (там есть `_to_local` в `backend/api/items.py`).
- Проверки — те же, что у сервисов: у встречи есть начало, конец позже начала, новая дата не в прошлом, точный дубль не создаётся. Перенос начала встречи без конца сохраняет длительность — это уже делает `update_record`.
- `ok=False` от сервиса → 422 с `detail` из `ActionResult.error` (текст сервиса уже человеческий). Записи нет или она чужая → 404. Тело не по схеме → 422.
- `None` в `UpdateItem` — «не менять». Убрать дату этим эндпоинтом нельзя, как и голосом.
- Удаление мягкое: «Удалить» — `status = cancelled`, «Вернуть» — `status = active` по тому же `id`. Насовсем запись стирает только чистка через 30 дней (backend-04).

### Сервисы под маршруты
- `update_record` и `set_status` принимают `record_id` уже найденной записи — цель искать не нужно. `update_record` принимает действие агента `UpdateRecord`, в котором обязательна цель `target` (`TargetRef`) — сервис её не использует. Как соединить `UpdateItem` с сервисом (адаптер в маршруте или правка сигнатуры с Денисом) — решаешь ты. `shift_minutes` наружу не отдаётся: кнопка всегда знает новое время.
- `create_record` встречу без времени (`time_given=false`) не сохраняет, а возвращает `missing=["start"]` — для кнопки это 422 «нужно время».
- Сервисы не коммитят. Как в `/api/chat`, коммитит маршрут: один запрос — одна транзакция, при ошибке — откат.

### Ручная правка и чат
Состояние разговора хранит `last_action` — последнее изменение для «нет, в 16» и «верни» ([`data-model.md`](../contracts/data-model.md), «Состояние разговора»). Пример, который ломается без правила: голосом «перенеси встречу на пятницу» (`last_action.before` = четверг), потом кнопкой на субботу, потом в чате «верни» — встреча откатится на четверг поверх ручной правки, а пользователь ждал другого. Поэтому решение техлида:
- изменение из интерфейса **не пишется** в состояние разговора;
- но **сбрасывает `last_action`** во всех разговорах пользователя, если оно затрагивает эту запись (у массового действия — если запись среди `record_ids`); тогда «верни» в чате честно скажет, что откатывать нечего;
- номера на экране (`shown`) и фокус не трогаются: запись та же, номер тот же.
Состояние — таблица `conversation_states`, сервисы — `backend/services/conversation.py`.

### Что уже есть в `develop`
- `GET /api/items` — `backend/api/items.py`: образец маршрута, пользователя, `tz` и ответа в поясе.
- `POST /api/chat` — `backend/api/chat.py`: образец одного коммита на запрос.
- Схемы — `backend/schemas/`; новые `CreateItem`, `UpdateItem`, `SetItemStatus` — оттуда же, поля строго из контракта.

## Критерии готовности
- [ ] Три эндпоинта работают по контракту: создание, перенос, выполнено, удалить и вернуть; ответы — `ActionResult` с датами в поясе `tz`.
- [ ] Встреча, перенесённая на занятое время, сохраняется, в `conflicts` — пересечения; дата в прошлом, конец раньше начала, встреча без времени, дубль → 422 с текстом сервиса; чужая или несуществующая запись → 404.
- [ ] Удалённая кнопкой запись пропадает из `GET /api/items`, «Вернуть» возвращает её с тем же `id`.
- [ ] Ручная правка сбрасывает `last_action` разговоров, где оно касается этой записи, и не трогает остальное состояние; после неё «верни» в чате не откатывает запись.
- [ ] Ошибка посреди запроса не оставляет полусохранённых изменений.
- [ ] Тесты `pytest` на каждый эндпоинт, каждый код ответа и сброс `last_action`.
- [ ] `/docs` показывает эндпоинты, тела и коды; `docs/modules/backend.md` — раздел «Записи из интерфейса».

## На усмотрение исполнителя
Устройство маршрутов, как `UpdateItem` попадает в `update_record`, как найти разговоры с этой записью в `last_action`, тесты.
