# agent-03: управление состоянием разговора и слот-филлинг

**Исполнитель:** Давид

## Цель
Реализовать механизм многошагового сбора параметров (Сценарий 2: доспрос недостающих полей), слияние аргументов черновика (`pending_action`) при голосовом ответе без отправки истории переписки в LLM, и прямое применение выбранного значения из UI без расхода токенов.

## Контекст
- **Стек:** Python 3.13, Pydantic v2, SQLAlchemy 2 (по техническим решениям в `docs/decisions.md`).
- **Контрактная основа:** Контракты [`docs/contracts/agent-tools.md`](../contracts/agent-tools.md) (инструмент `AskUser`), [`docs/contracts/api.md`](../contracts/api.md) (`ChatResponse.awaiting`), сервисный слой Дениса ([backend-02a](backend-02a-servisy-zapisej.md)).
- **Проблема наивных чат-ботов:**
  Пересылка всей простыни диалога на каждом шаге сжигает тысячи токенов и быстро исчерпывает минутные лимиты бесплатных тарифов API.
- **Архитектура легковесного состояния (Slot Filling):**
  Состояние живёт на сервере в таблице `conversation_states`. При нехватке параметров сервер сохраняет черновик в поле `pending_action: dict`.
- **Жизненный цикл Сценария 2 (создание встречи в два шага):**
  1. **Ход 1 (запрос без времени):**
     - Пользователь: *«Поставь встречу с Денисом»*.
     - LLM: либо вызывает `AskUser(question="На какое время назначить встречу?", missing=["start"])`, либо вызывает `CreateRecord(type="meeting", title="Встреча с Денисом", start=None, time_given=False)`.
     - Валидатор фиксирует: для `meeting` обязательно поле `start`.
     - Сервер сохраняет черновик: `state.pending_action = {"type": "meeting", "title": "Встреча с Денисом"}`, `state.missing = ["start"]`, `state.awaiting = "answer"`.
     - Клиент получает: `ChatResponse(reply="На какое время назначить встречу с Денисом?", awaiting="answer")`.
  2. **Ход 2 (ответ голосом):**
     - Пользователь: *«В 15:00»*.
     - В системный промпт второго хода инжектируется всего **одна строка якоря**:
       `[Активный черновик: встреча 'Встреча с Денисом', не хватает: start]`.
       (Предыдущие сообщения в LLM **не передаются**!).
     - LLM возвращает `CreateRecord(start="2026-10-25T15:00:00+03:00", time_given=True)` в формате `YYYY-MM-DDTHH:MM:SS+03:00`.
     - Сервер вызывает функцию слияния: новые поля сливаются с `state.pending_action`.
     - Все обязательные слоты собраны: запись создаётся в БД, `state.pending_action = None`, `state.focus_record_id = new_record.id`.
     - Клиент получает: `ChatResponse(reply="Встреча с Денисом создана на 15:00", result=ActionResult(ok=True, items=[new_record]), awaiting=None)`.
  3. **Ход 2 (клик в интерфейсе — детерминированный путь без LLM):**
     - Фронтенд Насти видит `awaiting="answer"` и `missing=["start"]` и отображает интерактивные чипы времени под сообщением (`[10:00]`, `[14:00]`, `[18:00]`).
     - Пользователь кликает по кнопке `15:00`.
     - Фронтенд отправляет точное ISO-значение на бэкенд.
     - Бэкенд валидирует дату и вливает её в `state.pending_action` **напрямую кодом сервиса без обращения к LLM**.
     - Расход: **0 токенов**, время ответа: **~15 мс**.
- **Разрешение контекстных ссылок («её / эту запись»):**
  - Любое завершённое действие обновляет `state.focus_record_id`.
  - Если в запросе пользователя содержатся местоимения («перенеси её», «удали её»), в контекст LLM подставляется:
    `[В фокусе: id={record.id}, '{record.title}', {record.start}]`.
  - Модель передаёт `record_id` из фокуса в аргументы действия.

### Источники для изучения
- **Паттерн сохранения промежуточного контекста без истории сообщений:** телефонный ассистент [livekit-booking-system](https://github.com/Basit-Arif/livekit-booking-system/blob/93e6e4cf1d8402bf797ec786a5364f5d8e4aa5b6/src/services/context_manager.py) (файл `src/services/context_manager.py`). Посмотри, как сервис отслеживает незаполненные поля бронирования и доспрашивает только их, не загружая в LLM весь диалог целиком.
- **Инструмент прерывания и доспроса пользователя:** проект [agents-from-scratch](https://github.com/langchain-ai/agents-from-scratch/blob/main/src/email_assistant/email_assistant_hitl_memory.py) (файл `src/email_assistant/email_assistant_hitl_memory.py`, паттерн `Question`). Демонстрирует, как явный инструмент вопроса структурирует диалог и сообщает бэкенду точный список недостающих полей.

## Критерии готовности
- [ ] Отрабатывает двухшаговый Сценарий 2: создание встречи без времени инициирует `AskUser` и переход в режим ожидания `awaiting="answer"`.
- [ ] На втором шаге в системный промпт передаётся только строка якоря черновика без истории сообщений.
- [ ] Реализован путь прямого закрытия слота из запроса с готовым значением без вызова внешнего API LLM (0 токенов).
- [ ] После сохранения записи черновик очищается, а идентификатор записи сохраняется в `state.focus_record_id`.
- [ ] Написан 1 быстрый смоук-тест через `pytest`, проверяющий формирование строки контекста черновика по объекту `ConversationState`.

## На усмотрение исполнителя
Время жизни (TTL) незавершённого черновика (например, сброс черновика при отсутствии активности более 15 минут), формат текстового представления якоря в промпте.
