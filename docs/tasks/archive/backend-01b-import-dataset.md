# backend-01b: импорт и инициализация датасета

**Исполнитель:** Денис

## Цель
Реализовать модуль загрузки и инициализации стартового датасета (1000 записей из CSV) для нового пользователя при его первом визите, чтобы списки за период и смысловой поиск были сразу доступны для демонстрации.

## Контекст
- **Стек:** Python 3.13, Pydantic v2, SQLAlchemy 2, PostgreSQL (по техническим решениям в `docs/decisions.md`).
- **Зависимость:** Выполняется после [backend-01a](backend-01a-shema-bd.md) (таблицы в базе данных уже созданы миграциями).
- **Исходные данные:**
  - Файл `voice_assistant_events_1000.csv` находится в репозитории по пути `backend/data/voice_assistant_events_1000.csv`.
  - Датасет содержит 1000 строк реальных событий ассистента с полями времени, даты и текста.
  - 376 уникальных текстов на 1000 строк — это разные события с разными датами, а не дубликаты.
- **Правила интерпретации данных при импорте (`docs/decisions.md`):**
  1. **Часовой пояс пользователя:**
     Время в строках CSV интерпретируется как локальное время в часовом поясе пользователя — том, что пришёл из браузера (`timezone` в запросе): «10:00» у любого пользователя остаётся 10:00. Значения преобразуются в `datetime` со смещением часового пояса (`AwareDatetime`).
  2. **Определение типа записи (`RecordType`):**
     - Встреча, созвон, демо, планёрка → тип `meeting`.
     - «Напомнить» → тип `reminder`.
     - Все остальные записи (в том числе «Позвонить …») → тип `task`.
     - Особенность данных: слово «встреча» есть и в задачах — «Отправить итоги встречи …», «Подготовиться к встрече …» (это `task`); «планёрка» в начале текста не стоит — «Провести планёрку …» (это `meeting`).
  3. **Определение статуса (`RecordStatus`):**
     - Если дата и время события находятся в прошлом относительно момента запуска импорта → статус `done`.
     - Если дата и время события находятся в будущем → статус `active`.
  4. **Идемпотентность:**
     - Импорт проверяет, есть ли уже записи у данного `user_id`. Если записи уже существуют, повторный импорт пропускается без создания дубликатов.
  5. **Изоляция:**
     - Все создаваемые записи привязываются строго к переданному `user_id`.
- **Интерфейс модуля (`backend/services/bootstrap.py`):**
  - Функция `bootstrap_user_data(db_session, user_id: UUID, timezone_str: str) -> int`: выполняет импорт и возвращает количество загруженных записей.
  - CLI-команда или скрипт для ручного наполнения базы данных при тестировании: `python -m backend.scripts.load_dataset --user-id <UUID>`.

### Источники для изучения
- **Пакетная вставка данных (bulk insert) в SQLAlchemy 2:** официальная документация [SQLAlchemy ORM Bulk Insert](https://docs.sqlalchemy.org/en/20/orm/queryguide/dml.html#bulk-insert). Паттерн создания записей через `insert(Record).values([...])` одним SQL-запросом вместо 1000 вызовов `session.add()` — импорт выполняется при первом визите пользователя, поэтому должен быть быстрым.

## Критерии готовности
- [ ] Функция `bootstrap_user_data` успешно загружает 1000 записей из CSV-файла в таблицу `records` для указанного `user_id`.
- [ ] Все даты и время в базе сохранены со смещением указанного часового пояса.
- [ ] Записи корректно распределены по типам (`meeting`, `reminder`, `task`) и статусам (`done`, `active`).
- [ ] Повторный вызов функции для того же `user_id` не создаёт дублирующих записей (идемпотентность).
- [ ] Написан 1 смоук-тест через `pytest`, проверяющий загрузку 5 тестовых строк из фикстуры CSV.

## На усмотрение исполнителя
Организация структуры вспомогательного CLI-скрипта запуска, формат логирования процесса импорта.
