# agent-05: агент на настоящих сервисах и в `/api/chat`

**Исполнитель:** Илья

## Цель
Довести Сценарий 1 (создание задачи, встречи, напоминания) до конца: реплика из `POST /api/chat` проходит через агента, запись сохраняется в PostgreSQL, ответ возвращается пользователю. Продолжение [agent-02](agent-02-klient-llm-i-vyzov-tulov.md): её код (клиент LLM, вызов инструмента, `process_user_turn`, реестр `ACTIONS`) уже в `develop`, а два её критерия — сохранение в PostgreSQL и `/api/chat` через агента — ждали сервисов и маршрутов бэкенда. Эта постановка их заменяет.

## Контекст
- **Что уже есть в `develop`:** `backend/agent/` — `process_user_turn`, `get_action`, `ACTIONS` с заглушками (`handle_create_record` собирает `Record` без сохранения), шаблоны ответа, обработка ошибок LLM. Устройство описано в [`docs/modules/agent.md`](../../modules/agent.md).
- **Зависимости:** сервисы записей [backend-02a](backend-02a-servisy-zapisej.md) (`backend/services/records.py::create_record`) и маршруты [backend-02b](backend-02b-api-routes.md) (`POST /api/chat`). Подключение `create_record` можно делать, как только backend-02a в `develop`; `/api/chat` — после backend-02b.
- **Сервисы синхронные, агент асинхронный** ([`docs/decisions.md`](../../decisions.md), «Доступ к БД»). Синхронный вызов базы прямо внутри `async def` блокирует весь сервер: пока идёт запрос одного пользователя, остальные ждут. Поэтому агент вызывает сервисы через `asyncio.to_thread`. Это касается всех вызовов сервисов из агента, не только `create_record`.
- **Транзакции:** сервисы Дениса сами делают `commit` (и `create_record`, и `save_conversation_state`). Значит «создать запись» и «сохранить состояние разговора» — две отдельные транзакции. Для Сценария 1 это допустимо; если найдёшь случай, где это ломает данные, — опиши его в `docs/modules/agent.md`.
- **Контракты:** [`agent-tools.md`](../../contracts/agent-tools.md) (действия, правила дат, период `[date_from, date_to)`), [`data-model.md`](../../contracts/data-model.md) (дата без времени: `start` — начало дня, `all_day`), [`api.md`](../../contracts/api.md) (`ChatRequest`, `ChatResponse`, `llm_config`). Ошибки бизнес-правил сервис возвращает в `ActionResult(ok=False, error=...)`, не исключением.
- **Граница с соседними задачами:** список за период и поиск — [agent-04](agent-04-scenarii-spiska-i-poiska.md); черновик и уточнения (`pending`, `merge_pending`, `clear_pending`) — [agent-03](agent-03-slot-filling-i-kontekst.md) у Давида. Здесь — только создание записи и стык с API.
- **Реальный провайдер ещё не проверялся.** Схемы инструментов содержат `$defs`/`$ref` и `anyOf` с `null`; вызов идёт с `tool_choice="required"`. Принимает ли это Gemini через OpenAI-совместимый адрес (`LLM_BASE_URL` в `.env.example`), неизвестно — это первое, что нужно проверить живым запросом.

## Критерии готовности
- [ ] Фраза «Поставь встречу с Иваном завтра в 15:00» через `POST /api/chat` создаёт запись в PostgreSQL с правильным временем и поясом пользователя; ответ подтверждает дату и время.
- [ ] «Купить хлеб завтра» сохраняется как задача на весь день (`all_day = true`); ответ без «00:00».
- [ ] Ошибка бизнес-правил (например, дата в прошлом) возвращается пользователю понятным текстом, без 500.
- [ ] Сервисы вызываются из агента без блокировки сервера (через `asyncio.to_thread`).
- [ ] Живой запрос к провайдеру по умолчанию (Gemini) проходит с нашими схемами и `tool_choice="required"`; результат проверки (что приняло, что пришлось поменять) записан в `docs/modules/agent.md`.
- [ ] Смоук-тест `pytest` без сети: агент с подменённым `get_action` вызывает настоящий `create_record` и возвращает созданную запись (тест с базой можно пропускать без `DATABASE_URL`, как `tests/test_db_smoke.py`).
