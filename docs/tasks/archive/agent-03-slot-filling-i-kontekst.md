# agent-03: управление состоянием разговора и слот-филлинг

**Исполнитель:** Давид

## Цель
Реализовать многошаговый сбор параметров (Сценарий 2: доспрос недостающих полей): ответ пользователя дополняет черновик (`pending`), история переписки в LLM не отправляется.

## Контекст
- **Стек:** Python 3.13, Pydantic v2, SQLAlchemy 2 (по техническим решениям в `docs/decisions.md`).
- **Контрактная основа:** Контракты [`docs/contracts/agent-tools.md`](../../contracts/agent-tools.md) (инструмент `AskUser`), [`docs/contracts/api.md`](../../contracts/api.md) (`ChatResponse.awaiting`), сервисный слой Дениса ([backend-02a](backend-02a-servisy-zapisej.md)).
- **Проблема наивных чат-ботов:**
  Пересылка всей простыни диалога на каждом шаге сжигает тысячи токенов и быстро исчерпывает минутные лимиты бесплатных тарифов API.
- **Архитектура легковесного состояния (Slot Filling):**
  Состояние живёт на сервере в таблице `conversation_states`. При нехватке параметров сервер сохраняет черновик в состоянии разговора — поля `pending`, `missing`, `awaiting`, `candidates` строго по `ConversationState` в [`docs/contracts/data-model.md`](../../contracts/data-model.md).
- **Сценарий 2 (создание встречи в два шага):**
  - Пользователь: *«Поставь встречу с Денисом»* → ассистент: *«На какое время поставить встречу?»* (`ChatResponse.awaiting = "answer"`).
  - Пользователь: *«В 15:00»* → встреча создаётся с названием из первого шага и временем из второго; черновик очищается, созданная запись становится фокусом разговора.
  - Как именно LLM и код делят работу на каждом шаге (что возвращает модель, когда проверяется и сливается черновик) — проектируешь ты; учти, что ответ LLM разбирается в `LLMAction` ([agent-02](agent-02-klient-llm-i-vyzov-tulov.md)).
  - Ответ на вопрос всегда приходит обычным текстом в `ChatRequest.text` — и набранный, и выбранный в интерфейсе; отдельного канала для готовых значений в контракте нет.
- **Разрешение контекстных ссылок («её / эту запись»):**
  - Любое завершённое действие обновляет `state.focus_record_id`.
  - Если в запросе пользователя содержатся местоимения («перенеси её», «удали её»), в контекст LLM подставляется:
    `[В фокусе: id={record.id}, '{record.title}', {record.start}]`.
  - Модель передаёт `record_id` из фокуса в аргументы действия.

### Источники для изучения
- **Паттерн сохранения промежуточного контекста без истории сообщений:** телефонный ассистент [livekit-booking-system](https://github.com/Basit-Arif/livekit-booking-system/blob/93e6e4cf1d8402bf797ec786a5364f5d8e4aa5b6/src/services/context_manager.py) (файл `src/services/context_manager.py`). Посмотри, как сервис отслеживает незаполненные поля бронирования и доспрашивает только их, не загружая в LLM весь диалог целиком.
- **Вопрос пользователю — тоже инструмент:** учебный агент LangChain [agents-from-scratch](https://github.com/langchain-ai/agents-from-scratch/blob/603fc7a4ac6119004f43894395e504a1fefcc6c0/src/email_assistant/tools/default/email_tools.py) (файл `src/email_assistant/tools/default/email_tools.py`, класс `Question`). Модель не пишет вопрос свободным текстом, а вызывает инструмент — так сервер точно знает, что ассистент ждёт ответа. У них в `Question` только текст вопроса; список недостающих полей (`missing`) — наше дополнение в `AskUser`.

## Критерии готовности
- [ ] Отрабатывает двухшаговый Сценарий 2: создание встречи без времени инициирует `AskUser` и переход в режим ожидания `awaiting="answer"`.
- [ ] На втором шаге в системный промпт передаётся только строка якоря черновика без истории сообщений.
- [ ] После сохранения записи черновик очищается, а идентификатор записи сохраняется в `state.focus_record_id`.
- [ ] Написан 1 быстрый смоук-тест через `pytest`, проверяющий формирование строки контекста черновика по объекту `ConversationState`.

## На усмотрение исполнителя
Время жизни (TTL) незавершённого черновика (например, сброс черновика при отсутствии активности более 15 минут), формат текстового представления якоря в промпте.
