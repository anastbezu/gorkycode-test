# backend-03: изменение и статус записей, конфликты, список без конца периода, один коммит на реплику

**Исполнитель:** Денис

## Цель
Дать агенту сервисы для бонусных сценариев задания и для контекста разговора:
- перенести или изменить запись, отметить выполненной, отменить, вернуть — и откатить любое из этого («верни»);
- при создании и переносе встречи предупредить о пересечении с другой встречей и не создавать точный дубль;
- показать список без конца периода («какие у меня задачи?»);
- хранить в состоянии разговора показанный список, последнее действие и признак пропущенного черновика;
- сохранять запись и состояние разговора одной транзакцией.

Агент (Илья, Давид) вызывает эти сервисы в своих задачах ([agent-06](agent-06-sostoyanie-v-prompte.md), [agent-07](agent-07-izmenenie-status-otkat.md)); здесь — только сервисы, маршрут и хранилище.

### Транзакции: один коммит на реплику
Решение техлида ([`docs/decisions.md`](../../decisions.md), строка «Доступ к БД» уточняется в этом же PR). Сейчас каждый сервис делает `commit` сам (`create_record`, `save_conversation_state`, `get_or_create_conversation_state`). При переносе записи агент сначала меняет запись, потом сохраняет состояние с прежними значениями для «верни». Если второе упало, перенос остался, а откатить его нечем.

Поэтому:
- сервисы записей и состояния **не коммитят** — только `add`/`flush` в переданную сессию;
- коммитит **маршрут** `POST /api/chat` — один раз, после того как реплика обработана (сейчас — разборщиком, после agent-05 — агентом); при исключении — откат, ответ 500 как сейчас;
- импорт датасета новому пользователю (`bootstrap_if_new`, `services/bootstrap.py`) остаётся со своим коммитом: он выполняется до реплики и не должен пропасть, если реплика упала;
- `GET /api/items` только читает — коммит не нужен.

Илья в agent-05 заменит вызов разборщика на агента в том же месте `chat.py` — коммит после вызова остаётся твоим. Агент сам не коммитит.

### Изменение записи
- На вход — запись пользователя (по id) и только меняемые поля из `UpdateRecord`: `title`, `start`, `end`, `time_given`, `deadline`. Остальные поля не трогаются. `time_given=False` при новом `start` — запись «на весь день», как при создании.
- Проверки — как при создании (`validate_create`): пояс, конец позже начала, новое время не в прошлом. Ошибка — `ActionResult(ok=False, error=…)`, не исключение.
- Возвращает изменённую запись **и прежние значения изменённых полей** (например `{"start": "2026-10-22T15:00:00+03:00"}`) — агент кладёт их в `last_action.before`, по ним «верни» откатит изменение.
- Чужая или несуществующая запись — `ok=False` с понятной ошибкой.

### Смена статуса
- `active`, `done`, `cancelled` для одной записи; возвращает запись и прежний статус (для `before`).
- Отменённая запись не удаляется, только меняет статус — её можно вернуть (`active`).

### Откат
Агент откатывает `last_action` твоими же сервисами: изменение — прежними значениями через сервис изменения, смена статуса — прежним статусом, создание — отменой созданной записи (`cancelled`). Отдельный сервис отката не нужен, если твои сервисы это позволяют; проверь это тестом.

### Конфликт и дубль
- **Конфликт** — при создании и переносе **встречи**: другие активные встречи этого пользователя, пересекающиеся по времени. У встречи без `end` для проверки берётся 60 минут от `start`; в запись это не пишется. Встреча «на весь день» в проверке не участвует. Запись сохраняется, пересечения — в `ActionResult.conflicts`.
- **Точный дубль** — активная запись того же пользователя с тем же названием (без учёта регистра) и тем же `start`. Не создаётся: `ok=False`, `error`, существующая запись — в `records`.
- Пример: созвон с Альфой 22.10 12:00 без конца. Встреча с Анной 22.10 12:30 — создаётся, в `conflicts` — созвон. «Созвон с Альфой» 22.10 12:00 ещё раз — не создаётся.

### Список без конца периода
`ListRecords.date_to = None` — без верхней границы от `date_from`; в конец добавляются активные записи без даты (`list_undated_records`). Сортировка и исключение `cancelled` — как сейчас. Пока ты это не сделал, `date_to = None` уже может прийти от модели — сейчас запрос с `< NULL` вернёт пустой список.

### Состояние разговора
- Миграция `0003`: в `conversation_states` — `shown` (массив UUID, по умолчанию пустой), `last_action` (JSONB, может быть пустым), `pending_skipped` (bool, по умолчанию `false`).
- `get_*`/`save_conversation_state` читают и пишут новые поля; `focus_record_id` по-прежнему обнуляется при удалении записи (`ondelete SET NULL`). Записи в `shown` и `last_action` могут указывать на запись, которую потом отменили, — это нормально, агент это обработает.

## Критерии готовности
- [ ] Миграция `0003` применяется на чистой БД и поверх данных `0002`; новые поля состояния сохраняются и читаются.
- [ ] Сервисы записей и состояния не делают `commit`; `POST /api/chat` коммитит один раз за реплику. Тест: если после изменения записи сохранение состояния падает, ни запись, ни состояние не меняются.
- [ ] Изменение записи меняет только переданные поля и возвращает прежние значения; перенос в прошлое и чужая запись — `ok=False` с понятной ошибкой.
- [ ] Смена статуса работает для `done`, `cancelled`, `active` и возвращает прежний статус; отменённая запись пропадает из списка за период и возвращается после `active`.
- [ ] Откат изменения, смены статуса и создания возможен существующими сервисами — есть тест на каждый.
- [ ] Встреча, пересекающаяся с другой (в том числе с встречей без конца — правило 60 минут), создаётся и возвращает `conflicts`; то же при переносе; точный дубль не создаётся.
- [ ] Список с `date_to = None` отдаёт записи от `date_from` без верхней границы и в конце — записи без даты; отменённых нет.
- [ ] Смоук-тесты `pytest` на новые сервисы (с базой — пропускаются без `DATABASE_URL`, как `tests/test_db_smoke.py`); старые тесты проходят.
- [ ] `docs/modules/` описывает новые сервисы и порядок коммита.
