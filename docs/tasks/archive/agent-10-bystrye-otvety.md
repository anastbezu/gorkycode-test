## Цель
Под вопросом ассистента интерфейс рисует быстрые ответы — чипы с номерами записей, «Да, все / Отмена», чипы времени встречи. Для этого сервер в `ChatResponse.awaiting` прямо говорит, чего ждёт. Нажатие чипа — обычная реплика («номер 2», «да, все», «отмена», «в 15:00»), и сервер обрабатывает её так же надёжно, как если бы её сказали голосом.

## Контекст

### Что не так сейчас
`awaiting` — только `"answer"` и `"choice"`. На «Отмени всё на завтра» (массовая отмена, `set_status` с `all = True`) и на «Перенеси встречу» (подошли две) сервер отвечает одинаково: `candidates` и `"choice"`. Вопрос «На какое время поставить встречу?» — `"answer"`, как любой другой вопрос. Интерфейс не может понять, какие кнопки показать, а угадывать по тексту `reply` нельзя — текст меняется.

### Что решено
`awaiting: Literal["answer", "choice", "confirm", "time"] | None` в `ChatResponse` и `ConversationState`. Чип отправляет обычную реплику, отдельного API нет.

| `awaiting` | Когда | Чипы в интерфейсе | Что отправляет чип |
|---|---|---|---|
| `"choice"` | несколько подходящих записей для одного действия (как сейчас) | запись под номером N из `candidates` | «номер N» |
| `"confirm"` | массовое `set_status` (`all = True`): найдено 2–20 записей, спрашиваем подтверждение | «Да, все» и «Отмена» | «да, все» / «отмена» |
| `"time"` | вопрос о времени встречи, у которой день уже известен | 09:00, 13:00, 15:00, 18:00 | «в 09:00» и т. п. |
| `"answer"` | любой другой вопрос | нет | — |

### Что сделать
1. **Схемы.** `backend/schemas/api.py` (`ChatResponse.awaiting`) и `backend/schemas/conversation.py` (`ConversationState.awaiting`) — новый `Literal` один в один из контракта. Модель БД `backend/db/models.py`, ограничение `awaiting_values`, — те же четыре значения; миграция.
2. **`"confirm"`.** В `update_state` (`backend/agent/state.py`): кандидаты пришли от массового `set_status` (`all = True`) — `awaiting = "confirm"` вместо `"choice"`. Остальное как сейчас: `candidates`, `shown`, `pending`. Ответ «да, все» уже работает по `agent-tools.md` (`set_status` с `all = True` без описания применяется ко всем из `shown`) — проверь тестом, что он работает и после смены значения.
3. **Отказ.** «отмена» уже обрабатывается без LLM (`is_refusal`, `REFUSALS`): при любом ожидании ничего не меняется, ожидание снимается. Проверь тестом, что при `"confirm"` это так и ни одна запись не изменилась.
4. **«номер N» без LLM.** При `"choice"` и `"confirm"` реплика вида «номер N» (N — число от 1 до числа кандидатов, без учёта регистра и знаков препинания) разбирается кодом, без вызова модели: это `TargetRef(index=N)` для отложенного действия (`pending`) — как если бы модель вернула «вторую». N вне диапазона — ответ «Нет записи под номером N.», ожидание остаётся. Зачем без LLM: нажатие чипа должно срабатывать всегда и мгновенно, а вызов модели на каждый клик — лишние деньги и риск, что она поймёт не так. Где именно перехватить реплику — рядом с `is_refusal` в `process_user_turn` (`backend/agent/agent.py`) или иначе — решаешь ты.
5. **`"time"`.** Ставится, когда ассистент спрашивает время встречи: черновик создания (`AskUser.draft`) — встреча, день известен, времени нет. Как это определить по черновику и `missing` — решаешь ты; условие описать в `docs/modules/agent.md`. Ответ «в 15:00» дополняет черновик, как любой ответ на вопрос (agent-03, уже работает) — проверь тестом.
6. **Тексты `reply` не меняются** — это зона Маши (product-03).

### Чего не делать
- Не менять `ActionResult`, `Record`, эндпоинты.
- Не трогать фронтенд.
- Не расширять `REFUSALS` словом «нет»: «нет, в 16» — это ответ, а не отказ.

## Тесты (pytest, без вызова модели)
- Массовая отмена с 3 подходящими → `awaiting == "confirm"`, `candidates` — 3 записи; «да, все» → все три отменены, ожидание снято; «отмена» → ни одна не изменилась, ожидание снято.
- Две подходящие для переноса → `"choice"`; «номер 2» → перенесена вторая, модель не вызывалась (подменить клиент LLM так, чтобы вызов падал); «Номер 2.» — то же; «номер 5» → «Нет записи под номером 5.», ожидание `"choice"` осталось.
- «Назначь встречу с Игорем завтра» (действие модели подставлено в тесте) → `awaiting == "time"`; «в 15:00» → встреча создана на завтра 15:00.
- Вопрос не о времени (нет названия) → `"answer"`.
- Миграция: `upgrade` → значения принимаются; `downgrade` → `upgrade` на чистой базе.
- Автотест агента (agent-08) проходит.

## Критерии готовности
- [ ] `ChatResponse.awaiting` и `ConversationState.awaiting` — четыре значения по контракту; БД принимает их, миграция с `downgrade`.
- [ ] Массовая отмена или выполнение спрашивает подтверждение с `"confirm"`; «да, все» выполняет, «отмена» ничего не меняет.
- [ ] «номер N» при выборе и подтверждении работает без вызова модели; номер вне диапазона — понятный ответ.
- [ ] Вопрос о времени встречи приходит с `"time"`; ответ «в HH:MM» создаёт встречу.
- [ ] Тесты из списка есть и проходят, весь набор зелёный.
- [ ] `docs/modules/agent.md` — когда какое `awaiting`, «номер N» без модели, условие `"time"`.
- [ ] На стенде: «Отмени всё на завтра» (под демо-учёткой) → в ответе `awaiting: "confirm"` (видно в `/docs` или во вкладке «Сеть» браузера).

## На усмотрение исполнителя
Где перехватывать «номер N», как определять вопрос о времени по черновику, имена функций, номер миграции. Не на усмотрение: значения `awaiting` и что отправляют чипы (контракт), «номер N» без модели, «нет» не становится отказом.
