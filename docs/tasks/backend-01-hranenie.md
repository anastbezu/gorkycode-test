# backend-01: хранение записей и импорт датасета

**Исполнитель:** Денис

## Цель
Записи пользователей и состояние разговоров надёжно хранятся в PostgreSQL по контракту, схема разворачивается миграциями Alembic, а стартовый датасет (1000 записей) автоматически загружается новому пользователю для демонстрации списков и поиска.

## Контекст
- **Стек:** Python 3.13, Pydantic v2, SQLAlchemy 2, Alembic, psycopg 3, PostgreSQL + pgvector (`docs/decisions.md`). Контейнер базы данных уже описан в `docker-compose.yaml`.
- **Контрактная изоляция:** Модуль хранилища изолирован. Внешний мир (агент, API) общается с данными **только через Pydantic-схемы** из `backend/schemas/` ([`docs/contracts/data-model.md`](../contracts/data-model.md)). Внутренние ORM-модели SQLAlchemy (`backend/db/models.py`) наружу не импортируются.
- **Работа с уже начатыми ветками:**
  - Возьми наработки из своих веток `feature/backend-01-shema-bd` и `feature/backend-02-pydantic-schemas`.
  - В модели `backend/db/models.py::Record` **удали** поле `embedding: Mapped[list[float] | None] = mapped_column(Vector(1536))` и константу `EMBEDDING_DIM = 1536`. Модель эмбеддингов ещё не выбрана; поиск по смыслу — отдельный модуль Родиона, векторную колонку он добавит собственной миграцией.
  - Добавь в `backend/db/models.py` ORM-модель таблицы `conversation_states` по контракту `ConversationState` (поля: `conversation_id`, `user_id`, `focus_record_id`, `pending` в формате JSONB или TEXT, `candidates` в формате UUID ARRAY / JSONB).
  - Схемы Pydantic из `backend/schemas/` уже готовы и полностью соответствуют контрактам.
- **Миграции Alembic:**
  - Настрой Alembic (`alembic/`), чтобы схема БД создавалась повторяемо с нуля (`alembic upgrade head`).
  - Проверь, что расширение `vector` (`CREATE EXTENSION IF NOT EXISTS vector;`) активируется первой миграцией.
- **Датасет и стартовые данные (`docs/decisions.md`):**
  - Файл датасета: `voice_assistant_events_1000.csv` помещается в директорию `backend/data/` репозитория.
  - Новый пользователь (анонимный `user_id` браузера) при первом обращении получает копию 1000 записей как стартовые данные.
  - Время в CSV считается временем в часовом поясе пользователя: «10:00» у пользователя с поясом `Europe/Moscow` становится 10:00 MSK (`10:00+03:00`).
  - Тип записи выводится из текста: «Встреча» / «Созвон» / «Демо» / «Планёрка» → `meeting`; «Напомнить» → `reminder`; остальное → `task`.
  - Статус: прошлое относительно момента импорта — `done`, будущее — `active`.
  - 376 уникальных текстов на 1000 строк — это разные записи с разными датами, не дубли.
  - Импорт должен быть идемпотентным (не создавать дублей при повторных запросах того же пользователя).

### Источники для изучения
- Модель напоминания с проверкой часового пояса и флагом «весь день» — голосовой навык OpenVoiceOS Alerts, файл [util/alert.py](https://github.com/OpenVoiceOS/ovos-skill-alerts/blob/29d82d2e02080618aa54b0d58b18e499a531d3a3/util/alert.py) (модель `Alert` и метод `create`).
- Хранение состояния разговора отдельными полями, а не историей сообщений — телефонный ассистент livekit-booking: [src/services/redis_service.py](https://github.com/Basit-Arif/livekit-booking-system/blob/93e6e4cf1d8402bf797ec786a5364f5d8e4aa5b6/src/services/redis_service.py) (структура `BookingContext`, у нас аналогичная логика в PostgreSQL).

## Критерии готовности
- [ ] Схема базы данных создаётся миграциями Alembic с нуля на чистой БД (`alembic upgrade head`).
- [ ] В таблице `records` нет поля `embedding` (оставлено для модуля поиска Родиона).
- [ ] В БД есть таблица `conversation_states`, поддерживающая сохранение и чтение `ConversationState`.
- [ ] Время всегда сохраняется с часовым поясом (`timestamptz`); запись без часового пояса отклоняется.
- [ ] Записи одного `user_id` изолированы и не видны другому `user_id`.
- [ ] При первом появлении пользователя создаётся его персональная копия 1000 записей датасета с корректными типами и статусами.
- [ ] Повторный вызов импорта для того же пользователя не плодит дубликаты.
- [ ] Написаны базовые тесты на сохранение/чтение записей и состояния диалога (`pytest`).
- [ ] Устройство модуля описано в `docs/modules/backend.md`.

## На усмотрение исполнителя
Структура индексов таблицы `records`, формат хранения поля `pending` в таблице состояния (JSONB или сериализованный текст), внутренняя организация скрипта импорта.
